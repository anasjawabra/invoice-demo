## Data-service contract (`POST /api/list`, `rev.data.list`)
* `req.facets: ['product','origin','source','due']` → `res.facets = { product:[{key,labelAr,labelEn,count,collected,outstanding,gross,exclusionAmount}], origin:[{key:'central'|'internal',…same}], source:[{key (revenue source),…}], due:{ overdue:{count,amount}, notYetDue:{count,amount}, unknown:{count,amount} } }`, each computed over the population that matches ALL current filters EXCEPT that facet's own dimension (so the chart still shows the alternatives after a selection).
* New list filters: `filters.product` (product key), `filters.origin` (`central`|`internal`), `filters.dueState` (`overdue`|`not_due`|`unknown`), and `filters.state:'uncollected'` = every uncollected, non-cancelled invoice INCLUDING the excluded ones (what `/collection` lists today: 146 = 92 open + 54 excluded in the compact store).
* Rows: `priority:{level:'high'|'medium'|'low', why{ar,en}, factors:[{label{ar,en},value}]}` and `nextStep{ar,en}` when `req.withPriority` (transparent rule over unpaid amount, overdue age and evidence status — the same ranking inputs as the old worklist, no numeric score exposed).
* `res.sums` gains `count`, `collected`, `outstanding`, `exclusionAmount`, `gross`; `res.population` describes the register population in words keys (`paid`: collected + partial, …).
* CSV export (`/api/export.csv`) honours every filter, always exports ALL filtered rows (not the page), and its first comment line states «يشمل كل النتائج المصفّاة (N)» / “all N filtered results”.

## Implemented — data service (server/lists.js, 6 Nov 2026)
Tests: `npm run test:facets` (tests/list-facets.test.mjs, compact synthetic store, 15 groups; chained at the end of `npm test`). No route change: `POST /api/list` and `GET /api/export.csv` take the new fields as they are.

**Request** (`rev.data.list(scope, { filters, page, pageSize, sort, facets, withPriority })`)
* `facets: ['product','origin','source','due']` (any subset). `withPriority: true` adds `priority` + `nextStep` to the rows of the page.
* New `filters`: `product` (a product key or an array of keys, as in `iim.PRODUCTS`), `origin` (`central`|`internal`), `source` (a revenue-source key; the shared scope's `scope.source` works as before), `dueState` (`overdue`|`not_due`|`unknown`), `state:'uncollected'`, `category` (a collection class — the worklist's `category`, on top of `state`), `reason` (`none`|`any`|a rule id — the worklist's `reason`). A value that matches nothing returns an empty list (never widens).
* New sort keys: `priority` (level first, then the old ranking score inside a level), `uncollected` (outstanding + exclusionAmount). Existing: `issue`, `gross`, `outstanding`, `daysOverdue`, `collected`, `exclusionAmount`, `id`. Every key works for the uncollected population, ascending and descending; ties keep the store order.

**Response**
```
{ total, page, pageSize, rows,
  sums: { count, gross, exclusions, net, collected, outstanding, exclusionAmount },
  population: { key:'paid'|'uncollected'|'collected'|'partial'|'open'|'noncollected'|'all', labelAr, labelEn, includes:[…], count, fullyPaid, partlyPaid, unpaid, excluded, cancelled },
  facets?: {
    product: [{ key, labelAr, labelEn, count, collected, outstanding, gross, exclusionAmount }],   // real product names (iim.PRODUCTS), only buckets with count > 0, catalogue order — the page ranks them
    origin:  [{ key:'central'|'internal', … }],  source: [{ key:<revenue source>, … }],
    due: { overdue:{count,amount,excludedCount,excludedAmount}, notYetDue:{…}, unknown:{…}, excluded:{count,amount} } } }
```
* Each facet is computed in the same pass as the list over the rows that match every filter **except its own dimension** (product = `scope.product` + `filters.product`; origin = `scope.scopeType` + `filters.origin`; source = `scope.source` + `filters.source`; due = `filters.dueState`). Σ over the buckets of a product / origin / source facet = the list total (count and every measure). Rows that fail two dimensions belong to no facet.
* `exclusionAmount` of a bucket is the unpaid remainder of its excluded invoices; `outstanding` stays 0 for them (the engine's rule), so unpaid incl. excluded = outstanding + exclusionAmount.
* **`due` and excluded invoices**: `overdue/notYetDue/unknown.count|amount` cover the unpaid, NON-excluded population (Σ amount = `sums.outstanding` = the net unpaid). Excluded invoices are tallied apart: `excludedCount/excludedAmount` per bucket (classified by their own due date) and `due.excluded` in total, so `Σ count + due.excluded.count = list total` and `Σ amount + due.excluded.amount = total unpaid incl. excluded`. `filters.dueState` applies to excluded invoices too (a bucket's list = `count + excludedCount`). An invoice with nothing owed (fully paid, cancelled) has no due position, so it never matches a `dueState`; on the Collected register only the partly paid remainder appears in `due`. A missing due date is `unknown` — never overdue. Keep `scope.status` at `all` when the due position is chosen through `filters.dueState` (the facet leaves out only `dueState`).
* `population` — which invoices the list holds: `paid` = collected + partly paid (the register), `uncollected` = open + excluded. `fullyPaid` / `partlyPaid` / `unpaid` count the invoices of the list by their PAYMENT status (an excluded invoice keeps its own), `excluded` = invoices with an exclusion on the unpaid remainder.
* `state:'uncollected'` = every uncollected, non-cancelled invoice, excluded included — exactly the worklist with `includeExcluded:true`: same invoices, `Σ outstanding + Σ exclusionAmount` = the worklist `totalOutstanding` (the «إجمالي غير المحصّل (يشمل المستبعد)» figure). Verified in the test for four scopes. (Compact store, scope 2026-01-01…5 Nov: 145 invoices = 92 open + 53 excluded; 3.890 + 2.693 = 6.582 ×10⁹ SAR.)
* Rows (list): every row also gets `uncollected` (= outstanding + exclusionAmount). With `withPriority`: `priority: { level:'high'|'medium'|'low', why:{ar,en}, factors:[{label:{ar,en}, value:{ar,en}}] }` and `nextStep:{ar,en}`; both `null` for an invoice with nothing owed. No numeric score is exposed (the worklist() output is unchanged and still carries it for the Decision Room and the analysis).
* `nextStep` comes from the non-collection analysis action groups (`GROUPS[…].nextStep*`: settle the amount conflict · request the missing data · verify the proposed link · review the contract · follow the objection · monitor the enforcement order · document why an overdue invoice is unpaid · none while not yet due); an excluded invoice gets «مستبعدة من صافي غير المحصّل — لا إجراء تحصيل؛ راجع سبب الاستبعاد». It is a recommendation, never a recoverability judgement.
* Cache: the list cache key now holds every filter (the whole `filters` object), the requested facets, the sort and the CONTENT hash of decisions / links / file exclusions (the earlier overlay-cache bug); `bumpEpoch()` clears it.

**Priority rule** (`PRIORITY_RULES` + `priorityCore` in lists.js; deterministic; thresholds are store-wide so an invoice keeps its level whatever the user filters)
* Amount tier from the unpaid, non-excluded balances of the whole dataset at the cut-off (a deterministic sample of ≤ 100k invoices): **large** = at or above the 90th percentile, **medium** = at or above the 75th, otherwise small.
* **High**: overdue and ((more than 180 days overdue and amount ≥ medium) or (amount large and more than 30 days overdue)).
* **Medium**: overdue, not high, and (more than 90 days overdue or amount ≥ medium); also a large amount overdue only 1–30 days.
* **Low**: overdue 1–90 days with a small amount; not yet due; excluded (no collection action).
* Due date unavailable: medium for a large amount, otherwise low — never high (its age cannot be assessed).
* Caps (High → Medium): incomplete evidence (evidence quality < 0.8: an amount conflict, a missing payer identifier or several smaller gaps) or an objection under review.
* `why` is a plain sentence («مبلغ كبير ومتأخر أكثر من 180 يوماً»; capped: «…، لكن الدليل ناقص — تُحسم البيانات أولاً»); `factors` lists the three inputs (unpaid amount tier with its percentile, due position, evidence completeness) + «الاستبعاد» for an excluded invoice. Sorting by `priority` orders high → medium → low (descending) and, inside a level, by the former weighted score (amount 0.4 · aging 0.25 · actionability 0.25 · evidence 0.1).

**CSV** (`GET /api/export.csv?q=…`): honours every filter (the same `candidates()` as the list), exports ALL filtered rows (never the page; `page`, `sort` and `facets` are ignored), and the ONE comment line (line 1) reads `# يشمل كل النتائج المصفّاة (N) — includes all N filtered results · demo data: synthetic …`; the header stays on line 2 (existing consumers read it there). `priority` (`high|medium|low`, empty when nothing is owed) and `exclusion_flag` (`excluded` when an exclusion removed an unpaid remainder) are appended at the END of `EXPORT_COLUMNS`; no column moved. `npm run verify:exports` and the platform/exclusion/register tests still pass.

**Deviations / notes**: (1) the contract said a header «first comment line» + English: both are in the same single line so line 2 stays the header. (2) The compact store's default scope (2026-01-01 → 5 Nov) holds 145 uncollected invoices (92 open + 53 excluded) both by the worklist and by the list; the "146" of the brief is not reproduced by that scope — the two services agree exactly, which is what the parity test pins. (3) `due` carries the extra `excluded…` fields described above. (4) A bucket with no invoice is omitted from product / origin / source (a page that wants a fixed set adds the zeros itself).
