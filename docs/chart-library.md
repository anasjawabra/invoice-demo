# Chart library — contract, catalog and status (6 Nov 2026)

One library serves Smart Reports, the Dashboard, the analysis pages and every export. A chart is a **model block** (`src/data/reportModel.js`); one SVG drawing (`src/utils/chartDraw.js` + the modules that register into it) is used on screen, in the PDF/print document and (rasterised) in Word; PowerPoint gets a native editable chart where the kind allows it, otherwise a documented vector/image fallback. **Nothing in the picker is "supported" because its name is listed**: every kind has a status in §6, backed by a test.

## 1. Extension points (already in the code)
* `registerDraw(kind, (c) => finish(c, height, svg))` and `drawKit` (makeCtx helpers, niceScale, wrapText, palette, `unitHead`, `colFrame`, …) — exported by `src/utils/chartDraw.js`. A new renderer module calls `registerDraw` at import time; `chartDraw.js` is NOT edited by renderer modules. The drawing rules in the header of `chartDraw.js` apply to every kind (zero baseline for bars, missing ≠ zero, one unit named once, Arabic mirrored as a whole, no clipped labels, `role=img` + aria-label + `<title>`, `data-i`/`data-j` drill hooks, tooltips with exact SAR).
* `registerChartFormat(kind, { info?, summary?, table? })` — exported by `src/data/reportFormat.js`: how a kind is unit-resolved, summarised in one sentence (aria-label) and tabulated (the accessible «View data table» and the export tables). A renderer module registers its kinds' formats next to its drawers.
* Renderer modules must be imported once by a side-effect import added to `src/utils/chartDraw.js`'s consumers: the single place is **`src/utils/chartKinds.js`** (created by the catalog agent: `import './chartDrawCartesian'; import './chartDrawHier';` …) and imported by `ReportChart.jsx`, `pdfReport.js`, `exportReportModel.js`, `pptxDeckPlan.js` and the tests.

## 2. Block shapes (extends the existing contract; existing kinds are unchanged)
Common optional fields on every chart block: `id` (stable within a report, `<sectionKey>:<n>`; set by `assignChartIds(model)`), `dim` (semantic descriptor, below), `alts` (pre-computed companion datasets, below), `config` (the applied presentation config, §4 — never a data change).

`dim` = `{ dimension:'amanah'|'municipality'|'source'|'product'|'month'|'aging'|'reason'|'entity'|…, ordered:boolean, measures:[{key:'net'|'collected'|'uncollected'|'excluded'|'rate'|'count'|'days'|…, kind:'amount'|'rate'|'count'|'days'}], additive:boolean, whole?:{label, value} }`. `additive:true` = the series are non-overlapping parts of one whole (stackable, pie-able). When `dim` is absent the catalog infers conservatively and prefers "unavailable" over a wrong chart.

Kinds (renderer `kind` → fields). **Cartesian family** (module `chartDrawCartesian.js`):
* `bar` clustered column (exists). `stacked_col`: `labels` × `series` stacked (additive). `stacked100_col` and `stacked100_hbar`: same data as stacked, each category scaled to 100 % (axis in %, tooltips carry amount AND share). `hbar` (exists), `stacked_hbar` (exists; amounts stacked per row).
* `line` (exists; `markers:true` draws markers; `basis:'monthly'|'cumulative'` stays explicit). `area` / `stacked_area`: ordered axis, `stacked_area` additive only.
* `combo`: series carry `type:'bar'|'line'` and `axis:'primary'|'secondary'`; the secondary axis has its own title/format (`block.axis2 = { title, kind:'rate'|'amount'|'count' }`) and is labelled as such (never mixes %-points with amounts on one axis).
* `pareto`: ONE nonnegative series; drawn sorted descending as bars + a cumulative-share line (0–100 %) on a secondary axis; Top N with an explicit «Other» group when `block.otherLabel` is set (the group is the summed remainder, never dropped).
* `histogram`: `bins:[{lo,hi,count,amount?}]`, `binUnit:'sar'|'days'`, `xTitle`; counts (or amounts) on the y axis; the bins cover every observation exactly once.
* `box`: `groups:[{label, n, min, q1, median, q3, max, outliers?:[…]}]`, `valueTitle`, `valueKind:'amount'|'days'`; drawn only for groups with `n >= 5` (others listed in the note as «not enough observations»).
* `scatter`: `points:[{x,y,label,key?}]`, `xTitle`, `yTitle`, `xKind`, `yKind` (`amount|rate|days|count`). `bubble`: same + `size` per point, `sizeTitle`, `sizeKind`. Neither implies causation (a fixed caption says so).
* `bullet`: `bullets:[{label, actual, target, ranges?:[{to,label}]}]`, `valueTitle`; `target` must come from an approved source (planning targets) — a row without an approved target is not drawn and is listed in the note; never an invented target.

**Hierarchy / flow family** (module `chartDrawHier.js`):
* `donut` (≤ 8 parts, nonnegative, one total; centre label = total with its unit).
* `treemap`: `tree:{label, value, children:[…]}` (leaf values are additive; parents = sum of children, verified) or a flat single series (one level).
* `sunburst`: `tree` with 2–3 levels (Amanah → municipality → revenue source), same additivity rule; root = the scope total.
* `sankey`: `nodes:[{id,label,col}]`, `links:[{from,to,value}]`; reconciled: for every intermediate node inflow = outflow (±0.5 SAR), no amount appears twice; the builder refuses (`null`) otherwise.
Existing `pie`, `waterfall`, `stacked_hbar`, `heatmap` stay as they are.

`alts` (built by the report model from the same verified numbers, at report build time, saved with the report): `{ scatter?, bubble?, histogram?, box?, sankey?, sunburst?, treemap?, bullet?, <dimension>:{…} }` — each is a ready block payload of the shape above. A switch to a data-dependent kind uses the matching `alts` entry; **no `alts` entry ⇒ the option is «unavailable — needs …»** (data-dependent). Switching never recomputes from the data service, so a presentation change cannot refresh figures.

## 3. Catalog (`src/data/chartCatalog.js` + `src/data/chartConfig.js`, pure, no React)
`chartConfig.js` holds the machinery (profile of a block, type rules, transformations, builders, `planConfig`); `chartCatalog.js` adds the type list, the picker's options and `evaluateChart`. `reportView.js` applies them per chart.

**`CHART_TYPES`** = 24 entries `{ id, kind, markers?, purpose, more, ar, en, useAr, useEn, needs, needsText, export:{pdf:'vector', word:'png', pptx:'native'|'vector-image'|'table', note:{ar,en}|null}, previewSpec }`. A table is not a type (it is the separate «View data table»).
`PURPOSES` order: **Comparison · Trend · Composition · Distribution · Relationship**. `more:true` (listed under «More charts»): `stacked100_col`, `stacked100_hbar`, `combo`, `treemap`, `sunburst`, `bubble`, `histogram`, `box`, `pareto`, `bullet`, `sankey`. Ids: `bar` (column; clustered when several series), `hbar`, `stacked_col`, `stacked_hbar`, `stacked100_col`, `stacked100_hbar`, `line`, `line_markers` (kind `line` + `markers:true`), `area`, `stacked_area`, `combo`, `waterfall`, `pie`, `donut`, `treemap`, `sunburst`, `heatmap`, `scatter`, `bubble`, `histogram`, `box`, `pareto`, `bullet`, `sankey`.
`previewSpec` = a tiny fixed synthetic block (`plain:true`, neutral labels A…E, no currency) drawable with `chartSvg` — a picture of the SHAPE, never the user's data; the UI may draw the user's own data instead when the type is available. The `export.pptx` column equals `PPTX_SUPPORT` of `src/utils/pptxCharts.js` (a test keeps them equal, with the same fallback wording).

**API** (all pure; none throws on odd input):
* `chartOptions(block, opts?) → { recommended, current, available:[{id, changes:[{key,ar,en}]}], unavailable:[{id, reason:{ar,en}}] }` — every type is in exactly one list; the current type is always available.
* `evaluateChart(block, typeId, cfg?, opts?) → { ok, reason?, typeId, block, changes:[{key,ar,en}], ignored:[{key,ar,en}] }` — validates BEFORE switching and returns the display block. `typeId` wins over `cfg.kind`; `typeId` in the result is the type after the orientation / grouping / percentage modifiers (e.g. `bar` + `grouping:'stacked'` → `stacked_col`). When `ok:false`, `block` is the base block unchanged. `ignored` = config knobs that do not apply here (sorting a time axis, a running total of a rate, a dimension the saved model lacks…), each with a reason — never an error. `opts = { lang }` (default: inferred from the block text) and `{ loose:true }` (the legacy global command only: an undescribed order / parts-of-a-whole is given the benefit of the doubt).
* `recommendedKind(block) → typeId` — the type the builder chose, unless the data reads better in another one that is available (many or long-named categories → `hbar`; a line over an unordered axis → `bar`; a pie of more than 8 parts → `hbar`).
* `defaultConfig(block) → cfg` (reproduces the block); `patchConfig(cfg, patch)` (switching `kind` resets the modifiers that came from the old kind); `normalizeConfig(cfg)`; `resolveType(cfg, block)`.
* `applyChartConfig(baseBlock, cfg, opts?) → displayBlock` (never mutates; the same numbers; an invalid request returns the base block; applying the same config again returns the same object) and `configChanges(block, cfg, opts?) → [{key,ar,en}]` for the preview text before «Apply».
* `chartDimensions(block) → [{id, current}]` — the dimensions the saved model already holds as `alts[<dimension>] = { labels, series, dim? }`.
* `exportEntryFor(block)`, and in `reportView.js`: `exportPlan(model, view) → [{chartId, title, kind, typeId, pdf:'vector', word:'png', pptx:'native'|'vector-image'|'table', note}]` (a model that already carries `model.view` is not viewed twice).
* Validators (exported, pure): `isAdditiveTree(tree, tol=0.5)`, `treeDepth`, `sankeyReconciles(payload, tol=0.5)` / `sankeyCheck` (→ `{ok, reason}`), `waterfallReconciles`, `histogramCheck`, `boxDrawable`, `bulletRows`.

**Compatibility rules** (a type that does not fit is `unavailable` with a reason that says what data is missing; the PDF/Word/PPTX exports draw exactly what the screen shows):
| Type | Available when |
|---|---|
| `bar`, `hbar` | a category × series block (not a waterfall / matrix / hierarchy / flow / XY / distribution block); all series in the same unit (an amount next to a rate or a count cannot share one axis → use `combo`). |
| `stacked_*`, `stacked100_*` | ≥ 2 series, `dim.additive` (or both roles `collected`+`uncollected`) — **net billed vs collected are NOT additive; collected + uncollected are**; no negatives, no missing values, not cumulative; `100 %` also needs a non-zero total per category. |
| `line`, `line_markers` | ordered axis (`dim.ordered`, month-like or bucket labels, or `basis` monthly/cumulative) and ≥ 2 points; a gap stays a gap. An unordered axis (Amanahs…) → «no meaningful order». |
| `area` | line rules + no gaps, no negatives, one series (overlapping areas hide each other). `stacked_area`: additive, ordered, no gaps. |
| `combo` | ordered axis, ≥ 2 series, ≤ 2 units; the first unit = columns on the primary axis, the other unit = a line on a secondary axis (`block.axis2 = {title, kind}`); same unit → first series columns, the others lines. |
| `waterfall` | **never produced from a table**: only itself, or from a reconciling `alts.waterfall`. A waterfall block is never converted — every other table-derived type is unavailable (use «View data table»); `alts`-based types (e.g. `sankey`) can still be offered. |
| `pie`, `donut` | one summable, non-negative, non-cumulative measure of parts of ONE whole (`dim` present, or `dim.partsOfWhole`), no gaps, non-zero total, ≥ 2 parts; or ≥ 2 additive series for a single category (the series become the parts). > 8 parts → the 7 largest + an explicit «Other». `dim.whole.value` larger than the shown parts adds «Other (rest of total)»; smaller → unavailable. |
| `treemap` | one summable non-negative single series of parts (flat, one level), or a saved additive tree (`alts.treemap`/`alts.sunburst`). `sunburst`: a saved additive tree with 2–3 levels below the root. |
| `heatmap` | one measure across two dimensions (`dim.seriesBy:'dimension'`, same unit, ≥ 2 × 2, non-negative), or `alts.heatmap`. |
| `scatter` | `alts.scatter` (≥ 3 valid points) or ≥ 2 series of two different measures with ≥ 3 complete categories (not cumulative). Categories missing a measure are omitted and the omission is stated. Always captioned «not causation». `bubble`: + a non-negative third series (the size) or `alts.bubble`. |
| `histogram` | `alts.histogram` (contiguous, ordered bins with counts, total > 0). |
| `box` | `alts.box` with ≥ 1 group of n ≥ 5 and ordered statistics (min ≤ q1 ≤ median ≤ q3 ≤ max). |
| `pareto` | one summable non-negative series of ≥ 3 categories, parts of a whole; sorted descending; > 20 categories → Top 15 + «Other». |
| `bullet` | `alts.bullet` with `targetApproved:true` and ≥ 1 row with a numeric target (never an invented target). |
| `sankey` | `alts.sankey` that reconciles: links join known nodes left to right, no pair linked twice, every intermediate node inflow = outflow (± 0.5 SAR), ≥ 1 source and sink. |

**Switch messages (`changes[]`)**, in AR + EN, each with a `key`: `grouping` (stacked ↔ grouped), `percentage` (amount → 100 % / share, with the denominator named), `topn` (Top N + «Other», or the automatic fold of a pie / pareto), `basis` (monthly → cumulative), `order` (sorted), `aggregation` (the parts are the series / each category becomes a point / the figures come from the saved data of the report, not the table / a second axis), `dimension`.

**What the report model must provide (agent A2 / report builders).** `dim` (below) and `alts`. `dim` fields read by the catalog: `dimension`, `ordered` (boolean — without it only month-like / bucket labels or monthly/cumulative `basis` count as ordered), `measures:[{key, kind:'amount'|'rate'|'count'|'days'}]` aligned with `series` (one entry applies to all), `additive` (series are non-overlapping parts), `seriesBy:'measure'|'dimension'` (default `measure`; `dimension` = the series are categories of a second dimension of ONE measure), `partsOfWhole` (override for single-series pies), `whole:{label,value}` (the stated total). `alts` payloads are ready blocks of the shapes in §2 (`scatter/bubble:{points,xTitle,yTitle,xKind,yKind,[sizeTitle,sizeKind]}`, `histogram:{bins,binUnit,xTitle}`, `box:{groups,valueTitle,valueKind}`, `bullet:{bullets,valueTitle,targetApproved:true}`, `sankey:{nodes,links}`, `sunburst|treemap:{tree}`, `waterfall:{labels,series,totals}`, `heatmap:{labels,series,valueKind}`, `<dimension>:{labels,series,dim?}`).

## 4. Chart config and persistence
`cfg = { kind, orientation:'v'|'h', mode:'amount'|'share', grouping:'grouped'|'stacked', cumulative:boolean, sort:'none'|'desc'|'asc'|'label', topN:number|null, labels:boolean|null, legend:boolean|null, dimension?:string }` — `kind` is a catalog type id. Every key is optional; **only explicit keys count** (`null` = not set). `labels` / `legend` are tri-state: `null`/absent = the renderer's automatic rule, `true`/`false` = forced (applied as `block.showLabels` / `block.showLegend`, which the renderers honour).
* **Modifiers pick the member of the bar family**: `orientation` (`bar` ↔ `hbar`, `stacked_col` ↔ `stacked_hbar`, …), `grouping` (`bar` ↔ `stacked_col`), `mode:'share'` (stacked → `stacked100_*`; for `bar`/`hbar`/`line`/`area` every value becomes its share of its series total, drawn as a percentage with the denominator stated; refused for rates, negatives, running totals). Explicit modifiers win over the ones implied by `kind`; use `patchConfig` so changing the kind drops the old kind's modifiers.
* **Monthly ↔ cumulative**: only for blocks that carry saved monthly values (`basis:'monthly'` or `dim.dimension:'month'`), summable measures and no missing month in the middle (trailing months not yet reported stay empty). The running sum is explicit (`basis:'cumulative'`, title suffix). The other way (cumulative → monthly) is refused: the monthly values of a cumulative chart are not saved.
* **Sort / Top N**: unordered axes only (a time axis is never re-ordered or truncated); the sort key is the first series, or the stack total for additive parts. Top N keeps the N largest rows and folds the rest into ONE explicit row «Other (k)» / «أخرى (k)» — summed per series (missing only when every folded value is missing), labelled, present in the table too (`block.otherIndex/otherCount/otherLabel`); the sums of every series are asserted unchanged before the result is returned; Top N on a rate is refused (it cannot be summed).
* **Dimension**: offered only for dimensions the saved model already holds in `alts` (otherwise `ignored` with «needs a new report version»).
* The applied config is stored on the display block as `block.config`; the base block is never mutated and a config never refreshes data.

**In the view.** `view = { chartKind, only, charts }` (`src/data/reportView.js`): `view.charts = { [chartId]: cfg }` next to the legacy `chartKind`/`only`. Chart ids come from `assignChartIds` (`<sectionKey|headline>:<n>`, independent of language/title). `applyView(model, view)` derives the displayed model from the saved immutable model: first the legacy global `chartKind` (now routed through `evaluateChart` — a waterfall / heat map / part-of-whole bar / running total is never converted; a chart the type does not fit is skipped), THEN each chart's own config. → `{ model, changed, skipped, skippedList:[{chartId,title,reason:{ar,en}}] }`. API: `setChartConfig(view, chartId, cfg, block?)` (with `block`, keys equal to the chart's own default are not stored; an empty config removes the entry), `resetChart(view, chartId)`, `chartConfigOf`, `cleanView` (reduces an untrusted view to its valid parts), `viewIsDefault` (covers `charts`), `exportPlan(model, view)`.
**Persistence.** The conversation keeps one `view` per result and per version on its messages (`kind:'view'` messages carry `baseId` + `view`); `reportStore.saveConvs` stores each message `view` through `cleanView`, so `view.charts` round-trips with the conversation and every version, and `applyView(restoredModel, restoredView)` reproduces exactly the charts that were shown (tested). The model records are untouched by a view.

## 5. Exports
PDF = the same SVG (every kind). Word = PNG of the SVG + the data table. PowerPoint = native editable chart where the kind has a native DrawingML form (see §6), otherwise a vector image (SVG with PNG fallback) with the data table in the appendix; the export dialog lists every fallback BEFORE export (`exportPlan`). The deck never substitutes another chart type silently.

## Hierarchy and flow renderers (module `src/utils/chartDrawHier.js`, helpers `src/data/chartTree.js`)
Kinds `donut`, `treemap`, `sunburst`, `sankey` — each with a drawer, a `registerChartFormat` (info / summary / table), tooltips with the exact SAR, drill hooks, Arabic mirrored as a whole, responsive down to 340 px, focusable marks when `interactive`, and legends/labels that honour `block.showLegend` / `block.showLabels` (both default on). Synthetic samples: `scripts/chart-samples-hier.mjs`; gallery: `scripts/make-chart-gallery-hier.mjs` → `scratch/chart-gallery-hier/`; tests: `tests/chart-hier.test.mjs` (`npm run test:charthier`).

**Never a wrong chart.** A block that is not parts of one whole is not drawn: the drawing is the «No data» / «لا بيانات» text plus a one-line reason, and the `<svg>` carries `data-refused="<code>"` (`negative`, `zero`, `missing`, `not-additive`, `not-reconciled`, `empty`, `flat`, `link`, `cycle`, …). The report builders and the catalog must use the same checks (pure, in `src/data/chartTree.js`): `treeIsAdditive(tree, tol=0.5)`, `treeProblem(tree, tol)` (→ `null` or `{code:'empty'|'missing'|'negative'|'sum', path}`), `treeTotal`, `flattenTree`, `treeDepth`, `treeFromSeries(labels, values, title)` (null items are returned in `missing`, never zero), `sankeyReconciles(nodes, links, tol=0.5)`, `sankeyProblem` (`empty|node|link|missing|negative|backward|cycle|duplicate|imbalance`), `sankeyColumns`.

| Kind | Block | Rules |
|---|---|---|
| `donut` | `labels`, `series[0].values`, optional `otherLabel` | Nonnegative parts of one total; any negative value or an all-zero total → refused. At most 8 slices: the 7 largest + one explicit «Other» slice (the summed remainder, labelled, members named in its tooltip, not a drill target); slices ordered by size, start at 12 o'clock; one positive part = the full ring. Zero and null parts draw no slice and stay in the legend (hollow swatch, «0» / «—»). Centre = total + unit. Legend rows = name · amount · share; slices ≥ 6 % carry their share. |
| `treemap` | `tree:{label,value,children}` (+ optional `levels:[…]` for the table headers, `colorBy:'group'\|'value'`) or a flat single series | Squarified, nested: parents are bordered groups with a name header (when they fit), leaves show name + share when they fit (otherwise the tooltip). Colour = top-level parent (default for ≥ 2 levels) or a value ramp (flat series). The tree must be additive within `block.tol` (0.5 SAR) and have no negative / null leaf. Zero leaves are not drawn (noted + in the table), null items of a flat series are listed as «no data (not zero)». |
| `sunburst` | `tree` (1–3+ levels below the root) | Rings = levels 1–3 (deeper levels only in the table, noted); angle ∝ value; root total + unit in the centre; each ring covers 2π exactly. A label is drawn only where its box lies inside the slice (name, else share) — slices that are too small are unlabelled but keep their true angle, tooltip and table row. A tree with no level below the root is refused (`flat`). |
| `sankey` | `nodes:[{id,label,col?,role?}]`, `links:[{from,to,value}]` | Reconciled: every node that has both inflow and outflow balances within `tol` (0.5 SAR); values nonnegative and non-null; every link goes to a later column (`col`, or inferred from the links); no duplicate `from>to`; otherwise refused. Band thickness = value × one scale (`data-w`/`data-v`); a link thinner than 1.5 px is drawn at 1.5 px and flagged `data-min="1"`. Zero links/nodes are not drawn (noted + in the table). Nodes ordered by barycentre sweeps (deterministic), y relaxed towards their neighbours. |

**Drill hooks.** Tree marks: `data-k="leaf|group|slice"`, `data-i` = index in `flattenTree(tree)` (pre-order, data order, root = 0), `data-j` = depth, `data-key` = `node.key` if given, else the path joined with ` › `. Donut: `data-k="slice"`, `data-i` = index in `block.labels`; the «Other» slice has `data-k="other"`, `data-key="__other"` and no drill. Sankey: nodes `data-k="node"`, `data-i` = node index, `data-key` = id; links `data-k="link"`, `data-i` = link index, `data-key` = `from>to`. With `interactive`, each is a focusable `role="button"` whose accessible name is its tooltip.

**Tables** (`chartTableText`): donut = part · amount (SAR) · share (+ «shown in the chart as» when grouped); tree kinds = one column per level (the full path, so a row stands alone) + amount (SAR) + share of parent + share of total, root first; sankey = from · to · amount (SAR). Amounts in tables are exact SAR; `block.plain` blocks (file-sourced numbers) are never labelled SAR.

**Limits.** Treemap areas are exactly proportional only among siblings of one parent (header/padding space makes the ratio drift slightly between parents; tooltips carry exact amount and shares, so area is never the only carrier). Sankey middle-column labels sit on the bands (white halo) and are cut at 340 px — the node tooltip has the full text. Colours cycle after 8 top-level groups (names, legend and tooltips still identify them). Sunburst shows at most 3 rings. PowerPoint: none of the four has a native DrawingML form here → vector image + data table (see §5/§6).

## Chart data (`dim`, `alts`, distributions) — agent A2, 6 Nov 2026
Every chart block built by `reportModel.js`, `ncReportModel.js`, `financialCharts.js` (and therefore the Dashboard export, `dashboardReport.js`) now carries a `dim`, a stable `id` and, where verified data supports it, `alts`. Builders live in **`src/data/chartAlts.js`** (pure); the invoice-level numbers come from **`server/distributions.js`** (route `POST /api/distributions`, wrapper `api.distributions`, provider `rev.data.distributions(scope, extra)` in both providers of `RevenueContext.jsx`). Tests: `npm run test:chartdata` (`tests/chart-data.test.mjs`, 20 groups, chained at the end of `npm test`).

**Reading a companion.** `resolveAlt(block, key)` (exported by `chartAlts.js`) is THE reader: a payload may say `inherit:'<altKey>'` (sunburst → treemap's `tree`; scatter → bubble's `points`) so the saved report does not store the same data twice; every other field of the payload (kind, title) overrides the inherited one. The catalog/`applyView` must read `block.alts[k]` through it. `block.altsNotes[k] = {ar,en}` states why an alternative is NOT offered (no approved target, fewer than 3 entities, distributions not attached); it is advisory text for the picker's «unavailable — needs …».

**Distributions payload** (`chartDistributions(st, req)`, same `req` as `snapshot`: scope, cfg, org permissions, overlays). Bins and quartiles only — never rows.
* `amount` — the snapshot's period cohort (issued in the period, in scope, measured at the same reference date), value = **gross billed per invoice**: `n = totals.count`; `bins` = 1-2-5 steps on a log scale, half-open `[lo,hi)`, only the contiguous range holding observations; `box.byAmanah`, `box.bySource`.
* `overdueStanding` — the aging chart's population (everything issued up to the cut-off and still owed, measured at the cut-off): `n + dueUnknown.count = Σ stock.aging[1..4].count`, `notDue.count = stock.aging[0].count`; equal-width day bins (width 30/60/90/180/365… so ≤ 16 bins; inclusive `[lo,hi]`); `box.byAmanah`.
* `overduePeriod` — the non-collection cohort (`n = populations.overdue.count`); same bin rule; `box.byAmanah`.
* `tree` — one row per Amanah × municipality group × source: net, collected, uncollected, count (the 3-level tree and the NC unpaid tree read it).
* Method (also in `payload.method` and in every note): quartiles = linear interpolation between order statistics (type 7, position (n−1)·p); whiskers = most extreme observation within 1.5×IQR, clamped to the box edge; outliers beyond (≤ 5 listed, `outlierCount` total); a group with n < 5 is **not drawn** (listed in `skipped` and in the block note). Statistics rounded to halalas.
* The builders accept a payload only if it describes THIS population (`amount.n === totals.count`; the standing/overdue counts reconcile as above); otherwise the histogram/box are simply not offered (`altsNotes`).
* **Wiring (callers):** `buildReportModel({ …, dist })`, `buildDashboardModel` (already calls `data.distributions` when present), and `buildNcReportModel(analysis)` reads `analysis.distributions`. Smart Reports' `generate()` should add `rev.data.distributions(ncScope, atEnd)` to its `Promise.all` and pass `dist` in `inputs` (kept in `_inputs`, so the other-language rebuild keeps it); the NC page should attach `distributions` next to `invoices`. `atEnd = { cfg: headlineCfg(rev.cfg) }` must be the same config as the snapshot's, otherwise the count check drops the payload.

**`dim` by chart** (`ordered` / `additive`): executive waterfall `step` (ordered, not additive) · collected+uncollected `status` (**additive**, whole = net billed) · monthly net/collected/received `month` (ordered, NOT additive) · cumulative line `month` · Amanah / source `hbar` (unordered, not additive: net vs collected overlap) · Amanah × source heat map (`rate`) · aging `aging` (ordered, additive, whole = standing balance) · exclusions by reason `reason` (additive, whole = exclusions) · NC: waterfall `step`; due position `due` (additive, whole = net unpaid); reasons (additive); age past due (ordered, additive); Amanah / source overdue (not additive: top N of the overdue part); heat map. Ranked hbars carry `otherLabel` (explicit «Other» row for Top N).

## Cartesian renderers (module `src/utils/chartDrawCartesian.js`, 6 Nov 2026)
Registers into `chartDraw.js` (`registerDraw`) and `reportFormat.js` (`registerChartFormat`: info · summary · table per kind). Tests: `npm run test:chartcart` (38 groups, AR + EN, w = 900 / 340 / fixed height); gallery: `npm run make:chart-gallery` → `scratch/chart-gallery/` (every kind AR + EN, plus a 340 px variant and a contact sheet `sheet.<lang>.html`). Synthetic sample blocks: `scripts/chart-samples-cartesian.mjs`.

**Common behaviour.** Every value axis is its own measure: `valueKind` (`amount` default · `rate` fractions 0..1 shown as % · `count` · `days`) + `valueTitle`; amounts use the chart unit (one per axis, named once in the axis title, exact SAR in every tooltip), rates are `%`, counts whole numbers, days plain. Marks: `data-i` = index into `labels` / `bins` / `groups` / `points` / `bullets` (for `pareto` the ORIGINAL index, not the sorted position), `data-j` = series (box: 0 = box, 1 = outlier; pareto: 0 = bar, 1 = cumulative point), `data-key` from `block.keys[i]` or `point.key`. `block.showLabels:false` drops value labels, `block.showLegend:false` drops the legend band (both honoured by the older kinds too through `legendPlan` / `valueLabel`), `block.orientation` (`'v'|'h'`) applies to the stacked family and `box`. Missing ≠ zero everywhere: a gap, a hatched/dashed tick or «—»; a zero draws no mark but is labelled 0 and stays hoverable. Segment / total labels are all-or-nothing per chart (they appear only when they fit every bar), so a chart never mixes labelled and unlabelled bars. Horizontal kinds draw at most 60 rows («+N more», the table keeps all).

| kind | block fields (beyond `labels` / `series`) | rules |
|---|---|---|
| `stacked_col` | — (`orientation:'h'` → rows) | positives stack up, negatives hang below zero (no total label for a mixed-sign category); an incomplete category (a part is `null`) draws the known parts and a «—» instead of a total |
| `stacked100_col`, `stacked100_hbar` | — (`orientation` flips) | axis 0–100 %; tooltip = amount (+ exact SAR) AND share; each category sums to 100 %; a zero / all-missing total is an empty «—» (never 0 %); negative parts → a «cannot be drawn» notice (`data-state="invalid"`) |
| `line` (extension) | `markers:true|false` | `true`: one marker SHAPE per series (circle · square · triangle · diamond), also in the legend, every point a drill target; `false`: lines only (isolated points keep a mark, all points stay hoverable); absent: the old circles, byte-identical |
| `area`, `stacked_area` | `basis` as for line | zero baseline; a missing value breaks the area (never drops to zero); a one-point segment is a narrow column; stacked: an index where ANY part is missing breaks the whole stack (its total would be understated), negatives refused |
| `combo` | series `type:'bar'|'line'`, `axis:'primary'|'secondary'`; `axis2:{title, kind}`; `valueKind`/`valueTitle` for the primary | two value axes each titled with its own unit; the legend names the axis of every series («left / right axis», mirrored in Arabic); if every series is secondary the single axis takes the `axis2` format |
| `pareto` | one series, `otherLabel` | sorted descending; the `otherLabel` group is excluded from the sort and always last (dashed, lighter); missing items follow the sorted ones with «—» and stay outside the total; cumulative line on a fixed 0–100 % axis, dashed 80 % line, caption «N of M items reach 80 %» (or «reached only with the Other group»); negatives refused |
| `histogram` | `bins:[{lo,hi,count,amount?}]`, `binUnit:'sar'|'days'`, `xTitle`, `valueKind:'count'|'amount'` | bars touch; empty bins stay (labelled 0, hoverable); x edges in the chart unit (K / M / bn SAR) or days; non-contiguous or open-ended bins get per-bin range labels; unequal widths draw at equal width with the caption «height = the bin's value, not a density» |
| `box` | `groups:[{label,n,min,q1,median,q3,max,outliers?}]`, `valueKind`, `valueTitle` | groups with `n < 5` or inconsistent statistics are not drawn and are named in the caption; ONE shared value axis (not forced through zero); horizontal when more than 8 groups drawn or `orientation:'h'`; a legend line explains the anatomy |
| `scatter`, `bubble` | `points:[{x,y,label,key?,size?}]`, `xKind`, `yKind`, `xTitle`, `yTitle`, `sizeKind`, `sizeTitle` | each axis has its own unit / format and a free (non-zero) scale; area ∝ size with 2–3 nested reference circles; labels only for the 6 largest bubbles (scatter: all ≤ 10 points, else the 4 extremes), all points keep tooltips with exact SAR; points missing a coordinate (or the size) are not drawn and counted in a caption; fixed caption «A relationship is not causation» inside the SVG footer |
| `bullet` | `bullets:[{label,actual,target,ranges?}]`, `valueKind`, `valueTitle` | a row without `target > 0` is not drawn and is named in the note (the table keeps it with «—»); bands from `ranges` (darkest = poorest), bar = actual, tick = target, text `actual / target = % achieved` (hidden with `showLabels:false`, still in the tooltip); one shared axis |

**Known limits.** No chart-level "other"/Top-N logic except pareto's `otherLabel` (the catalog's `applyChartConfig` does Top N upstream). `box` takes precomputed statistics (it never derives quartiles from observations). Bubble size legend uses rounded reference values (1/2/5 × 10ⁿ), so it shows magnitudes, not exact data. `combo` has at most two value axes and plots bars on the primary axis and lines on either. Rotated category labels are cut (26 characters, or what fits before the chart edge) with the full text in the tooltip. The scatter caption is drawn in the chart language only. PowerPoint/PDF specifics live in the export notes (this module only draws the SVG).

## Conversational chart requests (module `src/data/chartRequests.js`, agent F, 6 Nov 2026)
Pure, rule-based (Arabic + English keywords, the shared `normText` plus hamza / doubled-letter / one-letter-typo tolerance), no language model. It reads a message about the charts of the CURRENT result, finds WHICH chart it means and answers with one of four results — it never guesses between charts and never silently ignores a request. Tests: `npm run test:chartreq` (`tests/chart-requests.test.mjs`, 35 groups, chained at the end of `npm test`).

```
interpretChartRequest(q, { model, view, lang, base? }) →
  null                                                         not a chart request: the other interpreters run
  { type:'apply', chartId, chartTitle, patch, kind, note:{ar,en}, changes:[{key,ar,en}], ignored?, noop?, reset? }
  { type:'ask', question:{ar,en}, options:[{label:{ar,en}, text}] }                 several charts fit: one option per chart
  { type:'unsuitable', reason:{ar,en}, alternatives:[{typeId, label:{ar,en}, text}] } ≤ 4 ready alternatives (+ «View the data table» when charts cannot do it)
  { type:'need', question:{ar,en} }                                                  no result / no chart / no such chart / nothing to reset
viewAfterRequest(view, result, model) → the new view (setChartConfig / resetChart); the same view for every other result and for `noop`
```
* `model` = the result (saved model with `assignChartIds`, or the displayed one); `base` (optional, recommended) = the SAVED model the view is applied to. With `base` the chart is read as it is SHOWN under `view` (its type, dimension, title after earlier requests) and the new config is `patchConfig(view.charts[id], patch)` evaluated on the saved block, exactly what `applyView` will do — so `kind`, `changes` and `noop` are true to the screen. Without it `model` is taken as shown and only the patch is evaluated. `viewAfterRequest(…, model)`: pass the saved model to drop keys equal to the chart's own default (an empty config removes the entry); a displayed model (it carries `view`) is never used for that.
* `apply.patch` is a config patch (`{kind, orientation, mode, grouping, cumulative, sort, topN, labels, legend, dimension}`); `kind` is the resulting catalog type id; `changes` = the catalog's switch messages (percentage basis, grouping, Top N + Other, monthly → cumulative, order, dimension) **and they are repeated inside `note`** so the chat states them; `ignored` = requested knobs that do not apply, with the reason. `noop:true` = already shown that way (say so, no new card / Undo). `reset:true` = the config is removed.
* `ask.options[i].text` is a complete request that names its chart in quotes and parses back to the same request («اعرض "صافي المفوتر والمحصّل حسب الأمانة" كأعمدة», `Show "Exclusions by reason" as a donut chart`); the quoted title is matched against the chart titles (as saved and as shown). Titles are DATA: they are only compared with the words of the request, never read as instructions.

**Which chart.** Hard references first — «الرسم الأول/الثاني/…/الأخير», “chart 3”, a quoted title, a topic word next to a chart noun («الرسم الشهري», «رسم الاستبعادات», “the aging chart”, «الرسم التراكمي», “the line chart”, «رسم الشلال إلى أعمدة» = the waterfall as the SOURCE) — then soft selectors (a topic word, a measure word: «غير المحصل» / uncollected → the unpaid / overdue measures, «المقارنة» → a multi-series bar chart, «حسب X») narrow the candidates only when something matches; then each candidate is evaluated (`evaluateChart` with the merged config). One chart changes → `apply`; several → `ask`; all already so → `apply{noop}`; none → `unsuitable` with the most common catalog reason among the charts asked about (a waterfall's / heat map's own reason only if nothing else is left) and alternatives from `chartOptions(...).available` (same purpose as the requested type first, never the requested or current one; text ready to send).

**Rules.** A breakdown by a dimension the saved model does not hold (e.g. exclusions by municipality) → `unsuitable` with «needs a new report version» and the alternative text «قارن حسب البلدية» (the legacy command that ADDS that section from live data). «اعرض توزيع X حسب Y» is a breakdown (a ranked bar), not a histogram, unless the message says «توزيع المبالغ» / “distribution of amounts” / «مدرج تكراري». A data-dependent type without its `alts` → the catalog's reason ("needs …"). A waterfall is never turned into another type: the reason + Sankey (when `alts.sankey` exists) + the table. Stacking a non-additive pair, sorting a time axis, Top N on rates, cumulative → monthly: refused with the catalog's reason (never an unrelated chart). Top N keeps every series sum (explicit «Other» row). Percentages name their denominator (the `changes` message).
**Not a chart request → `null`:** report requests («أنشئ تقرير الأمانات», anything with تقرير/report or a period), exports («صدّر PDF»), questions («ما هو الرسم الدائري؟»), `show only the tables`, a bare «قارن حسب البلدية» (the legacy section command), a request that names a particular Amanah («قارن الرياض وجدة كأعمدة» asks for new figures; `resolveEntities`) unless it also names a chart, a request for a table («as a table»), and any message of the report interpreter's 579-sentence corpora (asserted; one deliberate exception: a bare «sort by amount descending» is a sort of the current charts). **Global phrases** («حوّل كل الرسوم إلى …»): `null` for what the legacy global command knows (columns / horizontal bars / line / pie) so it keeps working; for anything else (donut, treemap, hide the labels on all charts) an `ask` that goes chart by chart. The legacy command no longer reads «donut» as a pie (`CHART_KIND` in `chatIntents.js`).
**Known gaps.** No global reset («ارجع كل الرسوم…» → `null`); no memory of "the chart I just changed" beyond the view (a pronoun alone asks, one option per chart that changes); label / legend requests with several charts ask rather than apply to all; the note/changes text of the dimension switch is localised here but the catalog's other messages are used as they are (some mention "7 فئة"); synonyms outside the lists above («رسم كعكي» …) are not read; a message mixing two actions («اعرضه كأعمدة وصدّره PDF») is left to the export layer (`null`).

**Honest gaps.** (1) Word's PNG and PowerPoint's PNG fallback are proven structurally in Node, not pixel-wise; Microsoft PowerPoint itself was not opened. (2) The page picker is verified in the real app (Chrome pane), not by a DOM test runner. (7) A saved analysis whose cut-off is not the current one (or whose data changed) gets no histogram / box on screen or in its file — the count check would refuse them anyway.
