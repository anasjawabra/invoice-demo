# Smart Reports: export, PowerPoint template and conversation changes (5 Nov 2026)

## Implemented
* **Clutter removed:** «rule-based, not a language model», the demo-data sentence and the repeated scope chips are gone from the page and from exported reports (the report title is now «Key findings and insights»). The scope is shown once as a one-line summary that expands to all filters; examples and usage notes sit in a collapsed section. The synthetic-data provenance line stays on the title slide, on every content slide's footer and in the other formats.
* **One export action:** «تصدير التقرير» opens a dialog: format **PDF / PowerPoint** (Word, Excel, CSV under «other formats»), language **العربية / English**, report version when the conversation holds several reports. A report built from system data keeps its build inputs (not serialised), so it is re-expressed in the other language with the **same figures** (nothing is recalculated); a report without them offers only its own language. The dialog shows preparing / downloaded (file name) / failed-retry states. File names: `title_period_language.ext`.
* **History:** compact panel with search, Today / Yesterday / Earlier grouping, title, one-line preview, last update, active state, rename and delete.
* **PowerPoint on the supplied MOMAH template** (`public/templates/momah-{en,ar}.pptx`): the deck is built **inside the template package**, so masters, layouts, theme (teal palette, Trebuchet MS / Sakkal Majalla), logo, skyline, vertical rule, footers and slide numbers are the template's own. Title = «Title Slide», content = «Title Only», appendix divider = «Section header box», closing = «End»; the template's sample slides are removed. English → English template (LTR); Arabic → Arabic template (RTL, rule on the left). Everything is an editable PowerPoint object (text, tables, native charts); no screenshots. Code: `src/utils/pptxDeckPlan.js` (what goes on which slide), `src/utils/pptxCharts.js` (native chart parts), `src/utils/pptxTemplate.js` (slide parts + package assembly); `buildTemplatePptx` in `exportReportModel.js` wires them.
* **PowerPoint deck structure (concise main deck + appendix).** Main deck (about 20 slides for the detailed sample report): title (with «Version n · Generated … · Data as of …» when `model.meta` / `generatedAt` / `cutoff` exist; nothing is invented when they are absent) → **one** executive-summary slide (the indicators ONCE as cards + the summary sentence; no repeated KPI slides) → **one** scope-and-basis slide (filters, basis, cut-off, preparation time) → **one slide per chart or finding** (the chart + at most three evidence bullets computed from the chart's own data, the section's note / callout in italics, and a pointer to its appendix table) → the comparison table → key insights (the first six; all of them with figures, basis and caveat are in the appendix) → recommendations / findings from the records → notes and limits (callouts that do not belong to one chart, the forecast and its limits) → data and assumptions (provenance, including the synthetic-data line). Then the **Appendix**: a divider («الملحق / Appendix»), a contents slide (table number, title, slide number), and titled tables «الملحق أ-n / Appendix A.n» grouped by section: every table, every chart's data table, the financial-relationships table and the full insights table, **nothing dropped**; a long table continues on the next slide with its header repeated (row heights are predicted from the wrapped text, so a slide is never overfilled and a lone last row is never stranded). The footer carries the provenance line and the stamp on every slide. Sample counts (detailed report, compact synthetic data): Arabic 51 slides, English 52 (before: 51 / 51 with the heavy tables inline and the KPIs repeated); the main part is 20 slides in both languages.
* **Native, editable PowerPoint charts with embedded data.** Each chart is a real `p:graphicFrame` → `c:chartSpace` part (`ppt/charts/chartN.xml`) with its data caches and an **embedded workbook** (`ppt/embeddings/Microsoft_Excel_SheetN.xlsx`, sheet «Sheet1»: categories in column A, one column per series, an empty cell = no value), a chart relationship and a content-type override, so «Edit data» opens the numbers in PowerPoint. Series colours are the template theme's accents (`schemeClr`), text uses the theme minor font (`+mn-lt` / `+mn-cs`), values are in the chart's ONE unit (named once, in the value-axis title; a `basis` of monthly / cumulative is named there too), bars start at zero, a missing value is an empty cell and draws a gap (never a zero), a zero draws no bar but is labelled, data labels are hidden when crowded (lines then label only the last point). In the Arabic deck the chart text is right-to-left, columns and lines list their categories right to left (category axis reversed, value axis on the right) and horizontal bars grow from the right.
  * **Native chart kinds:** `bar` (clustered columns), `hbar` (clustered horizontal bars, first row on top), `line` (incl. dashed series, monthly / cumulative basis), `pie` (percentage labels), `stacked_hbar` (parts of one whole; each part's share % is written in its legend name at build time, so it does not update if the data are edited), `waterfall` (the standard stacked-column technique: an invisible «Base» series + Total / Decrease / Increase series, `totals` anchoring the absolute bars; the embedded sheet also lists the signed step values). A waterfall whose running total would cross zero cannot use the invisible-base technique and is built as a native clustered column chart of the signed step values.
  * **Native table, not a chart:** `heatmap` is a native PowerPoint table with shaded cells (lighter = lower, darker = higher; theme teal with lumMod / lumOff), hatched «—» cells where there is no data (never zero), and the highest / lowest cell as evidence bullets.
  * **Shape-based (editable vector shapes, NOT data-linked):** none of the current kinds. `chartShapes` (pptxTemplate.js) is no longer used by the planner: an unknown chart kind is NOT drawn as clustered columns any more (that was a silent substitution) — it gets a «no drawing for this chart kind» line and its data table.
  * **Chart-library kinds (6 Nov 2026) — status per kind** (full table and rules: `docs/chart-library.md` «Export support»). *Native, editable, embedded workbook:* `stacked_col`, `stacked100_col`, `stacked100_hbar` (percentStacked), `area`, `stacked_area`, `combo` (bars + lines, secondary axis with its own title), `pareto` (bars + cumulative line on a 0–100 % secondary axis), `histogram` (gap-free columns), `donut`, `scatter`, `bubble`. *Picture (SVG with PNG fallback, labelled «chart image — data in the table», data table in the appendix):* `bullet`, `box`, `treemap`, `sunburst`, `sankey`, and any block a native chart would misdraw (area with a missing value, donut > 8 parts). *Table:* `heatmap` (shaded native table). Never another chart type: an undrawable kind says so. PDF = the same SVG for every kind + its table; Word = PNG + table; Excel / CSV = the table + exact SAR.
* **How the deck was checked, and what that does not prove.** `verify:exports` (numeric parity) compares every table cell and every shown item of each model with the PowerPoint text (6,457 / 6,457 cells, 1,725 / 1,725 items across ten models incl. an English detailed report). That is a **numerical check only**; it is not proof of presentation quality, and it does not read chart data. Layout was judged by rendering both languages through LibreOffice and looking at every slide (overflow, overlap, clipping, empty slides, RTL), and structure was validated with python-pptx (every chart has its embedded workbook, relationships resolve, no duplicate shape ids, no leftover template slides) plus the PowerPoint chart-XML strictness rules (element order in `c:chartSpace` / `c:plotArea` / `c:ser` / `c:valAx`, unique `c:idx` / `c:order`, `c:cat` / `c:val` caches, `c:externalData` → embedded workbook relationship, content types). **The files were not opened in Microsoft PowerPoint** (not available here); LibreOffice places the value axis of an Arabic column chart on the left, whereas PowerPoint's reversed-category behaviour puts it on the right, so that detail is unverified.
* `npm run make:deck <dir>` builds, for visual inspection: the detailed report in Arabic and English, the same report re-expressed in the other language from its build inputs (Arabic→English and English→Arabic, as the export dialog does), a report without build inputs or meta, and sample decks with every chart kind (waterfall incl. one crossing zero, stacked bar, heat map with gaps, cumulative line with a dashed target, pie, a gap, plain numbers). They were rendered and inspected slide by slide and load in python-pptx with no broken relationship.

## PDF (a deliberately formatted print document, verified as real PDF files)
**Decision.** No PDF library is in the project and none of the candidates (pdf-lib, jsPDF, pdfmake) shapes Arabic by itself (joining, bidi, mixed numbers) or repeats table headers without hand-written layout code; adding one would have meant a custom Arabic text engine. The browser's own text engine does all of that, so the PDF is the browser's print of a **dedicated, isolated document** (not the app UI), designed for paper: `src/utils/pdfReport.js` (`buildPdfHtml(model, opts)`; `modelToHtml` in `exportReportModel.js` is a thin wrapper).
* **Flow.** «تصدير» → PDF opens the document in a new window (a preview with a bar: hint «choose “Save as PDF” and turn off Headers and footers» + a print button; the bar is never printed) and raises the print dialog once the fonts are loaded. The window title is the proposed file name (`reportFileName(model,'pdf')` without `.pdf`). If the pop-up is blocked, the same document is printed from a hidden iframe (this fallback was exercised in the dev app: isolated document, `lang`/`dir`, fonts loaded, no app chrome). The browser does the saving: the file name and the «Headers and footers» checkbox are the user's choices in that dialog.
* **Layout.** A4, margins 21/14/19 mm; CSS margin boxes: header = report title · «synthetic data — not the Ministry’s actual data», footer = version · prepared (Riyadh) · data cut-off · «Page X of Y» (`model.meta = {version, generatedAt, cutoff}` when present, else the model's own `generatedAt` / `cutoff`); a cover block (title, period, provenance, scope chips, KPI grid) instead of a cover page; headings keep with what follows; table `thead` repeats on every page; rows, KPI cards, insights, charts never split; the total is a styled last row (not a `tfoot`, which would repeat). Tables use fixed layout with proportional columns (label column 2–3 shares, numeric 1) so a ten-column table never squeezes its label column; tables of 10+ columns are set on **landscape pages** (named page `wide`). Numbers are tabular, never wrap, isolated left-to-right (`<bdi dir="ltr">`) and aligned to the column end; in Arabic text identifiers/ranges (`177-2200000123`, dates) are isolated too and a range arrow reads `←`. Every chart is followed by its «Chart data» table (heat maps as rows × columns with %, missing = «—»; waterfall signed; stacked bars with total and share %); charts come from `chartSvg` generically, and their text is forced onto the document font.
* **Fonts.** IBM Plex Sans Arabic 400/600/700 (Arabic + Latin subsets, the bundled `@fontsource` WOFF2 files) inlined as data URIs (`src/utils/pdfFonts.js`, Vite `?inline`; the dev server serves paths, which are fetched and inlined). No CDN, no network; verified by test (only `data:` URLs, no `http(s)`).
* **Verification.** `npm run make:report-pdf [outDir]` builds Arabic and English PDFs of a detailed synthetic report (+ a 70-row table, a 10-column table) with headless Chromium, then checks page count, `pdffonts` (all embedded), `pdftotext`, ink/words per page (no blank pages), numeric parity (every number of every KPI / table / chart-data cell of the model must occur in the PDF text at least as often; read from a render without the chart drawings because their bar-value labels sit side by side) and label parity (letter-multiset match, because poppler returns Arabic ligatures out of order). `npm run test:pdf` runs the 29 structural tests (A4 `@page`, margin boxes, `thead`, `dir`/`lang`, every cell present, no external URL, escaping, defensive `meta`). The PDFs were rendered to PNG and every page of both was looked at.
* **Limitations (stated plainly).** (1) It is still the browser's print: the user must pick «Save as PDF»; the running header/footer and page numbers use CSS margin boxes, which need Chrome / Edge 131+ (Safari and Firefox print the content without them). (2) Text is real, selectable text with the font embedded, but Arabic copy/search is viewer-dependent (poppler returns correct words with some lam-alef / letter-pair order glitches; pdf.js returns presentation-form glyphs in visual order). (3) A few symbols in model text (→ ✓ ≥ Σ) are not in IBM Plex Sans Arabic; the browser substitutes a system font for those glyphs (embedded subset: Arial / Tahoma / Lucida Grande on macOS). (4) The new-window path (pop-up allowed) was not exercised in the browser pane used for testing (it blocks pop-ups) — the iframe fallback was; the print dialog itself cannot be driven there, the PDFs come from headless Chromium running the same document. (5) A forced page break around landscape tables can leave part of a page empty.

## Page refinement (6 Nov 2026)
* **Removed completely:** the page-level scope line («النطاق الذي سيُستخدم / Scope that will be used: …» with its expandable control) and the «أمثلة وملاحظات الاستخدام / Examples and usage notes» block (heading, expandable content, borders, spacing; `SUPPORTED_HELP` is no longer imported). The applied scope stays in «كيف فهمتُ طلبك» and in each report's details; scope handling, interpretation and calculations are untouched.
* **Opening screen:** compact title + one-line description in the page itself (the duplicate header of `SmartReportsPage` is gone); «＋ محادثة جديدة» and «سجل المحادثات» aligned in the header (count shown only when > 0); the welcome is centred in the free workspace; three suggestions; attachment only through the composer.
* **History:** a compact drawer (dialog, Esc / ✕ / scrim close, focus returns to its button, the conversation state is untouched); search only when conversations exist; empty state «لا توجد محادثات محفوظة بعد» + «محادثة جديدة»; restore, rename, delete (with confirmation) and saved versions unchanged. The browser-local backup / restore panel (previously hidden inside the usage notes) now lives, collapsed, at the foot of the drawer so that function is not lost.
* **Composer:** the inner rectangular focus outline is removed; one subtle ring around the whole composer; states: disabled (greyed), ready (send turns primary), generating (stop button, red ring); keyboard hint small and hidden on phones; on mobile the dock stays compact and never covers the last report content (measured).
