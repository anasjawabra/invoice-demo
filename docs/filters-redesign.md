# Platform-wide filter redesign — requirements, page configuration and status (5 Nov 2026)

Goal: **better filtering with fewer visible controls — not more filters.** Compact, consistent, purpose-driven, honest.

## Requirements (from the user)
1. **Audit every page** (routes, existing filters, their real effect on queries, charts, tables, exports): per page the main tasks, essential / secondary / redundant / broken filters. Never copy one big panel everywhere.
2. **Shared compact toolbar**: one period selector (where relevant) + 2–3 page-specific essential filters (≤ 3–4 primary controls on desktop, excluding search and action buttons) + search where useful + **«المزيد من الفلاتر» / “More filters”** for secondary options + **«مسح الفلاتر» / “Clear filters”** only when something differs from the default. Labels ABOVE controls, consistent heights/widths/spacing. Advanced filters open in a popover (desktop) / drawer (mobile) / expandable panel.
3. **One period selector** with presets: This month · Previous month · This quarter · Year to date · All available data · Custom range. From/To inputs ONLY for custom range, explicit «من / إلى» labels, unambiguous date formatting, correct start/end meaning in RTL. State the **date basis** (invoice issue date · payment date · contract date · order date) per page; do not apply invoice dates automatically to every module.
4. **Filters by purpose** (starting point, refine after the audit):
| Page | Primary | Secondary |
|---|---|---|
| Dashboard `/insights` | Period, Amanah/entity, **municipality**, revenue source | supported comparison options |
| Collected invoices `/invoices` | Period (payment-date basis where appropriate), Amanah/entity, **municipality**, revenue source | Source system, partial/full payment |
| Uncollected `/collection` | Amanah/entity, **municipality**, revenue source, overdue / due position | Period, payment status, enforcement status |
| Exclusions `/exclusions` | Period, Amanah/entity, **municipality**, exclusion reason | Revenue source, source system |
| Investment contracts `/contracts` | Amanah/entity, contract status | Municipality, contract dates, verified installment/payment conditions |
| Enforcement `/enforcement` | Order status, Amanah/entity, linkage/review status | Source, order-date range |
| Collection planning `/planning` | Fiscal year, Amanah/entity | Supported plan / revenue dimensions |
Search matches the page's main identifiers (invoice no., contract no., order no., billed-party name). No unsupported filters, no duplicates. **Data Sources** and **Metrics/Glossary**: no financial filter panel. **Smart Reports**: one concise conversation-scope summary with an edit action, not the dashboard panel.
5. **Remove redundant dimensions**: «Revenue source» / «Product» / «Main revenue classification» — consolidate or move the less-used levels into advanced filters. Keep **source system** distinct from **revenue source** (clear labels). Municipality options depend on the selected Amanah; clear incompatible selections **visibly** when the parent changes. Never show entities outside the user's permissions.
6. **Active filters**: removable chips only for meaningful non-default selections; never several «All…» chips; the selected period in ONE concise place; result count near the table; the data cutoff separate from the date range; lengthy availability / methodology text behind an information control; an advanced filter stays visible as a chip after its panel closes; no repeating the same scope in subtitle + panel + summary.
7. **Predictable behaviour**: simple toolbar selections apply immediately; multi-control advanced panels use an explicit **Apply**. Filters drive KPIs, charts, lists, totals, reports and exports. Preserved through pagination, sorting, detail navigation and return (URL state where appropriate). No-results state explains and offers reset; never silently broaden the scope; unavailable ≠ zero.
8. Unchanged: approved financial calculations, composite invoice identity, permissions, data relationships. Exclusion ≠ payment status; enforcement closure ≠ payment; missing data ≠ zero; missing municipality ≠ another municipality; no new business classifications just to populate a filter.
9. Design: MOMAH/DGA tokens, IBM Plex Sans, project icons (Hugeicons unavailable locally — see docs/design-dependencies.md), shared components, Arabic RTL + English LTR, keyboard + accessible labels, **searchable dropdowns for long lists**, selected / loading / disabled states, mobile = compact **Filter** button + drawer with the active-filter count. No oversized cards, no large gaps, no panel that pushes content far down.
10. Validate every retained filter, dependent selections, counts/totals reconcile, exports respect filters, permissions, state survives detail navigation, reset + no-results, ar/en desktop + mobile. Deliver: page-by-page retained/removed list, before/after screenshots, validation results, remaining limitations.

## Architecture (implemented)
* `src/components/filters/` — shared building blocks; `ScopeFilters` = the toolbar bound to the shared revenue scope (`useRevenue()` scope setters), configured per page; `ScopeBar` (RevenueUI) now delegates to it.
* The scope is shared across pages (period, Amanah, source, … persist for the session) — "Clear filters" returns it to the defaults.

## Audit
Facts verified in code and in the running app (dev server, 5 Nov 2026, Arabic + English, 1440 / 375 px). «Really filters» = checked against the data service: the same shared scope sent to `api.snapshot` gives different, reconciling totals per field (base 419 invoices / 15 819 M gross; central 357 + internal 62 = 419 and 11 596 M + 4 223 M = 15 819 M; status overdue 58 invoices; product Furas 57; main class «استثمار» 70; Riyadh North municipality 19; source and Amanah likewise). Every field of the shared scope drives the KPIs, charts, lists and the dashboard export; nothing is cosmetic. (Amounts shown are synthetic demo data.)

## Components
All in `src/components/filters/` (import from `index.js`). Labels sit ABOVE controls; control height 36 px; IBM Plex via tokens; RTL/LTR by logical CSS properties (`.ft-*` at the end of `src/styles/revenue.css`). ≤ 720 px the toolbar collapses into ONE «تصفية / Filter» button with the active-filter count and a bottom drawer (every control + Apply / Clear).

* **`ScopeFilters`** `{ primary, secondary, dateBasis, search, actions, resultCount, extra, comparison, extraChips, onClearLocal, hideStatuses, onChange }` — bound to the shared revenue scope. Pick a page configuration: `<ScopeFilters {...FILTER_PAGES.collected} search={{ value, onChange, placeholder }} resultCount="…" />`. Keys: `period | amanah | municipality | source | status | duePosition | invoiceOrigin | product | mainClass | comparison | extra`. Amanah options = `org.amanahKeys`; municipality depends on the Amanah and is cleared **with a visible, aria-live notice** when the Amanah changes; an active scope filter that is not on the page's toolbar appears as a removable chip; «مسح الفلاتر» only when something is non-default → `resetScope` (+ `onClearLocal`). `onChange(patch)` is called after any change (reset the page number there).
* **`LocalFilterToolbar`** `{ fields, values?, onChange?, urlKeys, defaults, search, actions, resultCount, info, extraChips }` — same toolbar for local filters (contracts, enforcement, planning). `fields: [{ key, label:{ar,en}, type:'select'|'multi'|'period'|'text', options | (values)=>options, primary:true, group, dependsOn, clearedNotice, default, disabled, hint }]`. With `urlKeys` and no `values` the state is the URL (`useUrlFilters`, replace history, other params preserved, defaults omitted).
* **`FilterBar`** — the engine behind both (`defs`, `primary` keys, `values`, `onChange(patch)`); **`FilterToolbar`** — the layout shell (slots: primary, search, more, info, actions, chips, resultCount, drawer).
* **`FilterField`** `{ label, value, onChange, options, type, searchable, disabled, loading, hint }` — native select up to 12 options, accessible searchable combobox above 12 (arrow keys / Enter / Esc / type-ahead, Arabic-normalised), checkbox group for `multi`.
* **`PeriodSelect`** `{ preset, from, to, today, dateBasis, onPreset, onRange }` — one button «السنة حتى اليوم · 1 يناير – 5 نوفمبر 2026»; popover with the six choices; From / To only under «نطاق مخصص» (validated, typed date echoed in words); date-basis line; the data cutoff is NOT in it.
* **`MoreFilters`** `{ defs, values, onApply }` — «المزيد من الفلاتر» popover with its own draft, Apply / Cancel / Reset, count badge; applied advanced filters stay visible as chips.
* **`ActiveFilterChips`**, **`DataInfo`** (the «i» control: cutoff, source, date basis, reconciliation, rule version), **`useUrlFilters`**.
* **`FILTER_PAGES`** (`filterConfig.js`): `default`, `dashboard`, `decisions`, `collected`, `uncollected`, `exclusions`, `product`, and the local-page descriptors `contracts`, `enforcement`, `planning`. Pure helpers (`filterLogic.js`): defaults, chips, `cascadePatch`, `permittedAmanahOptions`, `validateCustomRange`, date-basis labels, URL round-trip — tested by `npm run test:filters` (21 checks).
* Product vs source system: the revenue source stays «مصدر الإيراد»; the only system-like filter that really works is Product (the platform an invoice comes from) and it is labelled «المنتج (المنصة)» inside «تصنيف الإيراد». No separate «source system» filter was added.

## Municipality as a primary control (6 Nov 2026 — supersedes the «Municipality in More filters» rows above)
`البلدية` is a visible primary control placed immediately after the Amanah selector on every page whose toolbar has the Amanah selector and whose data carries a municipality: Dashboard, Collected, Uncollected, Exclusions, Decision Room, Product (`FILTER_PAGES` in `src/components/filters/filterConfig.js`; Contracts and Planning have no municipality in their data; the Enforcement eligible-invoices toolbar keeps it in More until orders themselves carry one). Same `FilterField` style and height as the Amanah; a little narrower (`.ft-field--muni`, 190 px) so the four primary controls share one row at 1360 px (verified on all six pages: one row, no wrap). Disabled until ONE Amanah is chosen with the placeholder «اختر أمانة أولاً» / “Select an Amanah first” **inside** the control (a Housing-Sector selection reads «لا بلديات لهذه الجهة»); enabled: «كل البلديات» + the explicit groups + the Amanah's reference municipalities, searchable; changing / clearing the Amanah resets it with the aria-live notice «أُزيلت البلدية لأن الأمانة تغيّرت». On mobile the drawer lists it right after the Amanah. Because a primary control already shows its value, no chip duplicates it on desktop (chips of primary controls are left out, as for every primary control); on mobile the chip row shows it. Details: `docs/municipality-hierarchy.md`. Screenshots: `docs/screenshots/muni-filter-{disabled,jeddah,search,chip,reset,mobile}.jpg`.
