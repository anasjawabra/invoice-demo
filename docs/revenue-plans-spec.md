# Revenue plans — implementation contract («خطط الإيرادات»)

The contract every implementer builds against. Basis: `docs/planning-review/12-revenue-plans-analysis.md`, `13-revised-proposal.md` and the user's **corrections of 2026-11-07** (below, they win over 13). Agents append an «Implementation notes» section at the end for what they built and any limitation. Do NOT change financial definitions: approved identities (Net = Gross − Exclusions; Uncollected = Net − Collected; collection rate = Collected ÷ Net; target achievement = collected ÷ target) are untouched.

## 0. Defaults (implementation defaults — NOT claims of formal Finance approval)
1. States **draft / active / archived**. No approval workflow, approver, or word «معتمد/معتمدة» for plans anywhere in the new UI/API (use «فعّالة», «مفعّلة كأساس للتقارير»).
2. Period preset **January–December** — wherever the fiscal year is named, label it an assumption pending business confirmation.
3. Monthly distribution **explicit**: `equal` (labelled «توزيع متساوٍ — افتراض», never silent) or `manual`. Equal is exact (weights = 1 per whole month, day-fraction for a partial first/last month; see `planMath.distributionWeights`).
4. **No tolerance badge**, no «وفق الخطة / متقدم / متأخر» classification. Headline = signed monetary deviation + the ratio نسبة الإنجاز مقابل المخطط. The deviation % may live in a tooltip / detail / export, not a headline card.
5. Forecast = clearly labelled **recent-run-rate** (last three complete months) where data suffices; never a probability.

## 1. Data model (server-owned, shared)
Money = whole riyals (integers; `src/data/plans/planMath.js` — largest-remainder apportionment, rounding remainder always returned and shown). Months `'YYYY-MM'`, dates `'YYYY-MM-DD'`. Manual month weights = whole basis points, total must be exactly 10 000.

```
plan {
  id: 'plan-<8 hex>', type: 'baseline' | 'scenario', scenarioOf?: planId,        // scenario: model + rules only; the UI creates baselines; a scenario can never be activated
  state: 'draft' | 'active' | 'archived',
  createdBy: { userId, name } | null,        // null = UNKNOWN (seed / imported legacy). Immutable. name = snapshot; display resolves the current name from userId
  createdAt, updatedAt, lastEditedBy: { userId, name } | null,
  origin: 'user' | 'seed' | 'imported',      // seed = the illustrative demo baseline: always labelled «توضيحية», never "approved"
  legacy: { …original metadata verbatim: versionId, status, owner (free text), savedBy, savedAt, source:'device-localStorage' } | null,   // read-only record, never interpreted as owner/approval
  working: { content, lastEditedBy, updatedAt } | null,   // the editable DRAFT (never-activated plan) or a pending REVISION of an active plan; reports never read it
  versions: [ { n, content, activatedBy:{userId,name}|null, activatedAt, supersededAt|null } ],   // immutable snapshots, one per ACTIVATION
  inForce: n | null,                          // the version reports read (only while state === 'active')
  revision: int                                // optimistic-concurrency counter; +1 on EVERY mutation of the record
}
content {                                      // the versioned unit
  name, scope: { kind: 'ministry' } | { kind: 'entities', entityKeys: [...] },     // existing entity keys only (appropriation entities except the headquarters)
  period: { start, end, preset: 'fiscal-year' | 'range' },
  target: { amount: int|null, basis?: { method:'budget_x_coverage', coverage, budget, at } },   // basis = a NOTE, never a live dependency
  allocations: [ { entityKey, amount:int, origin:'manual'|'distributed'|'migrated'|'seed', note? } ],
  distribution: { profile: 'equal'|'manual'|null, weights?: { [ym]: basisPoints } },
  entityDistributions?: { [entityKey]: distribution },
  advanced: { collectionRate?: fraction, billingTarget?: int }                       // used ONLY by the billing-sufficiency factor
}
references: { [year]: { planId, setBy:{userId,name}, at } }          // explicit reference plan per calendar year for non-plan consumers
audit[]: { id, at, actor:{userId,name}|{system:true}, action, planId?, summary }   // never truncated
```
`planView(plan, which)` (pure, `src/data/plans/planRules.js`) → `{ planId, versionId ('plan-x@v3' | 'plan-x@draft'), versionNumber|null, name, state, type, origin, period, scope, content, isDraft, isHistorical, labelSource }` — the ONLY input the calculation core and the consumers read. `which` = 'inForce' (default) | 'working' | n.

## 2. Rules
**Validation levels.** *Draft save* hard errors only: invalid dates (end ≥ start), unknown/forbidden entity, scope outside the actor's authority, negative / non-numeric amounts or weights, a manual month outside the period. Everything else is allowed in a draft (unallocated or excess amounts, months ≠ 100 %, empty target, no profile).
*Activation* additionally requires ALL of: target > 0 · Σ allocations = target to the riyal (unallocated 0, excess 0) · every allocation inside the plan scope · explicit profile chosen · manual months total exactly 10 000 bp (and entity overrides too) · type = baseline · **no other ACTIVE baseline with the identical entity set and identical period** (blocked; names the plan; offer archive-the-other or revise-it) · actor authorised. Result = a check list with one entry per rule (id, ok, params).
**Overlaps are otherwise ALLOWED** (Ministry vs entity plan; annual vs a range inside it). Informational notes only. **Nothing is ever added across plans**: no screen or report sums targets of different plans; each figure comes from ONE plan.
**Allocation is top-down.** The target is fixed; rows distribute it. A new plan starts with NO rows (unallocated = target). Nothing is distributed, spread or recalculated implicitly — changing the target never edits rows. Explicit actions, each = pure preview then apply:
- `distributeRemainder` — basis `appropriation` (revenue-appropriation share, only where budget data exists) | `equal` | `proportional` (to current amounts); rows it may fill (default: empty rows only). Preview lists EVERY changed row (before/after/delta), the unallocated before/after and the **rounding remainder** (riyals + which rows received them). Rows with amounts change only if the user ticked them in.
- `redistributeAll` — same, for all rows.
Monthly: `distributionSummary` shows total, **remaining %**, excess; actions `distributeEqually` and `distributeRemaining` (over chosen months) with before/after preview; **never normalise silently** — a total ≠ 10 000 bp is shown and blocks activation only.
**Versions** = activations. Activation validates `working`, then in ONE atomic store write: appends the snapshot, sets `inForce`, supersedes the previous, clears `working`, state = active, revision+1, audit. A draft/revision save NEVER changes `versions`/`inForce` → active reports are unaffected until activation. Archive removes the plan from reporting (versions and audit kept); restore = active again only if the checks and the duplicate rule pass.
**Reference plan.** Non-plan consumers (Decision Room, dashboard target, Smart Reports, assistant, fixed reports, viewer targets) use an **explicitly configured reference plan per calendar year**. `resolveReferencePlan({year, plans, references})` → `{ state:'ok', plan, source:'configured'|'only_eligible' }` | `{ state:'ambiguous', candidates }` | `{ state:'none' }` | `{ state:'reference_invalid', reason }` (configured plan no longer active → surfaced, never silently replaced). Eligible = ACTIVE baselines whose in-force period overlaps the year. Exactly one eligible and no reference → used, source labelled «الخطة الوحيدة المؤهلة». >1 and none configured → **ambiguous: surfaced**. Every consumer shows the source plan name + version. The seed plan is configured as the 2026 reference with an audit event (actor = system). Ministry allocations and independent entity plans stay distinguishable: `allocationDifferences(entityPlanView, referenceView)` shows a per-entity difference and NEVER reconciles or replaces either value.
**Plan detail pages** use ONLY the selected plan and its selected version (in-force by default; working/older version read-only with a banner) for every metric, chart, forecast and action.
**Access.** Reads: module `planning`; a restricted viewer gets `maskPlanForViewer`: only the allocations of entities they may see, `target.amount` replaced by the visible Σ labelled «إجمالي الجهات المتاحة لك», no advanced/basis. Mutations: module `planning` AND role not read-only AND the actor's scope fully covers every entity of the plan (Ministry scope ⇒ all-entities access; entity scope ⇒ every entity with whole-Amanah grant) — enforced **server-side** (`403`), not only in the UI. Setting a reference plan needs all-entities access. No finer permission is invented.
**Ownership.** `createdBy` = the authenticated creator's stable user id (+ name snapshot); immutable; another user's edit changes only `lastEditedBy`/`updatedAt`. Seed and imported legacy plans have `createdBy: null` (unknown); no reassignment feature exists and none is needed.
**Legacy.** The browser's `ib_plan_targets_v1` record is preserved untouched. `legacyStoreToContent(store, year)` maps it to a content whose allocations are the old computed entity targets (`origin:'migrated'`) with the old monthly weights as a manual profile only when they are not all equal (else explicit equal); `legacyRecord(store, year)` keeps the original metadata verbatim. Import creates a **draft** (`origin:'imported'`, audit `import` with the importing user), never auto-active, and a device may import a year once.
**Seed.** If the store has no plans: one **active** baseline 2026, `origin:'seed'`, Ministry scope, fiscal-year preset, target = 66 % × the communicated budget (the old documented default; basis note recorded), allocations by revenue-appropriation share (`origin:'seed'`), explicit equal profile, name «خطة تحصيل 2026 — توضيحية (بيانات توضيحية)», set as the 2026 reference.

## 4. Persistence — what is and is not claimed
Pattern = the identity store: one JSON document `server/.data/plans.json` (git-ignored), written atomically (temp + rename), `IIM_PLANS_FILE` override, same fallbacks (OS temp dir, then memory). **Verified facts must be written in «Implementation notes»**: survives a process restart in file mode (test), shared by concurrent sessions (test). **It is a local-demo store.** On a read-only host filesystem (Vercel) it falls back to the temp dir / memory: not durable across cold starts and not shared across function instances. The feature must say so (a data-sources/readme note and the implementation notes), and must NOT be described as deployment-ready durable persistence.

## 5. Calculation core (pure)
`planningBasisFromPlan({ view, today, latestDataDate, entityKeys, actual })` — additive; the old store-based `planningBasis` keeps working until the cleanup phase. Period-aware: months = `planMath.monthRows(period)`; target = view content target; entity rows from allocations (entity override distribution else plan's); planned-to-date = `planMath.plannedTo`; actual = collections from period.start through the cut-off.
**Dates are distinct** and all carried on the result: `reportingCutoff` (min(today or period end, latest data date)), `latestActualDataDate`, `lastCompleteMonth` (the last month fully before the cut-off that is used to estimate the rate; may end BEFORE the cut-off and may start before the period), `forecastGeneratedAt` (timestamp).
**Forecast** (`forecastPlan`) = actual collected through the cut-off (partial-month actuals counted ONCE) + `rate × Σ over remaining period days (days after the cut-off to the period end, per month: days ÷ monthDays)`, rate = mean of the last three COMPLETE observed months (missing observations are excluded, never zero; fewer than three → state `insufficient_history`, no percentage). A history window ending before the cut-off is legitimate. **Reject** (state `incompatible_input`/`stale_input`, no number) inputs whose planId / versionId / scope / period / cut-off do not match the basis. Completed period → final actual achievement, no forecast. Future period → no forecast. Zero target → none. Expected achievement = forecast full-period collections ÷ full-period target (never a probability, never capped).
**Headline measures** (`planMeasures(basis, forecast)`): target; actual; `achievementToDate` = actual ÷ full-period target; `plannedToDate`; `vsPlanRatio` = actual ÷ plannedToDate; `deviation.amount` (signed), `deviation.pct` (tooltip/detail only); `expected.amount`, `expected.pct`, `expected.gap` (shortfall positive / surplus negative with explicit label). No `status`/tolerance classification field.

The old store-based `planningBasis` / `planTarget` / `forecastYear` / `loadPlanInputs` are untouched.
- **Lifecycle vs calculation state.** `basis.planState` = the plan's lifecycle (`view.state`); `basis.state` = the calculation state: ok · future_period · completed · no_target (`reason` zero_target | target_missing) · draft_incomplete · no_data (`reason` no_data_in_period | actual_not_loaded) · incompatible_input · stale_input · invalid_period. `forecast.state` adds insufficient_history · draft.
- **Input identity.** `loadPlanInputsForPlan` stamps `{planId, versionId, scopeKey, period, cutoff}` on `.actual.meta` and `.history`; the basis refuses a mismatched actual and `forecastPlan` a mismatched/unlabelled history (no numbers). `scopeKey` = `planScope(scope, entityKeys).key` (a restricted viewer's key includes the visible set).
- **Scope in the data service.** The engine's `resolveScope` takes `amanah` as a LIST, so an entity plan / restricted viewer is ONE snapshot + ONE series call (no per-entity fan-out); a history series call is added only when a history month is not a whole month inside the period.
- **Dates.** `reportingCutoff = min(today, period end, latest data date)`; `lastCompleteMonth` on the basis = the last calendar month fully on/before the cut-off (candidate), on the forecast = the last month actually used in the window; `forecastGeneratedAt` is set only by `forecastPlan` (`now` is injectable).
- **Limitations.** Months before `DATA_START` (2025-01-01) are null (not 0) and flagged (`flags.incompleteActual`, notice `data_gap`); planned-to-date still counts the whole plan. A draft's expected figure is withheld unless `allowDraft`. Charts/factors (`planningCharts`, `planningFactors`) still read the OLD basis shape (12-month year, `asOf`): D adapts presentation from `basis.months` / `basis.cumulative`.

## Persistence — verified facts and limitations
*(Rewritten 2026-11-07 for the simplified workflow of §10 — the earlier text spoke of draft / activation / revisions; those are gone. `tests/plans-server.test.mjs` = `npm run test:plansserver`, 23 tests.)*
**What the tests prove**
- **Restart persistence (file mode).** A store opened on a temp file is written through the HTTP API (create → update by another user → set the organisation reference → personal defaults); a FRESH `openPlanStore(file)` instance then reads back the identical document — plans, internal snapshots, audit, references, owner AND the per-user defaults (`userDefaults`) — edits continue on it, a third instance sees them, and the system plan is not seeded again. An unreadable or structurally wrong file is set aside (`plans.json.unreadable-<ts>`) and never half-trusted.
- **Concurrent sessions.** Two signed-in sessions (two tokens, two users) share one stored document inside the data service: B sees A's new plan in the list and by id, and A's later change; ownership (`createdBy` = the creator's stable user id) is immutable across another user's edit while `lastEditedBy`/`updatedAt` move; a stale `revision` is refused 409 `revision_conflict` naming the last editor, and nothing is overwritten.
- **Atomic save.** Every mutation runs on a clone of the document that is swapped in only on success; a failure injected at each step of a save (`save.snapshot`, `save.content`, `save.state`, `commit`, and `create.insert` for a create) leaves the stored document byte-identical (revision, content, snapshots, audit, defaults) and the answer carries no exception message.
- **Migration.** A store written in the OLD shape (schema 1: draft / active / archived plans with versions + inForce + working) is migrated in place when opened (schema 2); nothing is dropped, no owner is invented, it is idempotent, audited with one `migrate` event, and the pre-migration file is kept once as `plans.json.pre-v2.bak` (tested with every old combination including a plan holding both an in-force version and a pending working copy).
- **Access.** 401 / 403 module / 403 `read_only_role` / 403 `forbidden`+`reason` (`scope` | `municipality`) / 403 `system_plan_readonly` / 404-like-missing for plans a restricted viewer may not see; masked reads for restricted viewers; reference setting needs all-entities access; a personal default only for a plan the caller can see.
- **Hygiene.** No password / hash / secret / token-like string in any response, audit entry or the persisted file of the whole suite.

**What is NOT claimed.** This is a **LOCAL-DEMO store**, not durable, deployment-ready storage.
- Only `mode: 'file'` survives a restart, and only for the single process that owns that file. On a **read-only host such as Vercel** the store falls back to the OS temp directory (`tmp`) or process memory (`memory`): it is **not durable across cold starts and not shared across function instances** (each instance seeds its own illustrative system plan, and users' personal defaults live only as long as that store). `GET /plans` and `GET /plans/references` therefore return `storage: { mode, durable, localDemo: true }` so the UI can say so; the plans page must carry that note (see the UI contract).
- No cross-process locking: two server processes writing the same file can overwrite each other (single-process use only). `revision` guards concurrent sessions of ONE process (and any client that re-reads before writing), not concurrent processes.
- The whole document is rewritten on every mutation (fine at demo scale; a real database would replace the store module, not the service or the API). Internal snapshots grow by one per save and are never pruned.
- A write failure downgrades the store to memory (as the identity store does) instead of failing the request: the answer still succeeds, `storage.mode` then reads `memory`.

Parent and municipality records are never added together.
**One scope, everywhere.** The view scope drives targets, actuals, planned-to-date, forecast, percentages, charts, tables, action lines and exports on the detail page, and consumers (Decision Room, reports, assistant, exports) when they are given a municipality scope.
**Permissions (UI and API).** Visibility: a viewer sees an entity if any grant covers it, and a municipality only if their grant covers it.
