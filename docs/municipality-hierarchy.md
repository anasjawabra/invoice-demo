### Data-model contract (every invoice row, detail record and candidate carries it)
`amanahId` (demo stand-in for AMANA_NO), `amanahAr`, `amanahEn`;
`municipalityRefId` (MREF-…, null unless mapped) · `municipalityKey` (the filter value, always set: `<Amanah key>|<MREF-…>` or `<Amanah key>|NOT_SPECIFIED|DIRECT|UNRESOLVED`) · `municipalityAr` / `municipalityEn` (the reference name; null unless mapped; the reference has Arabic names only, so the English UI shows the Arabic name) · `municipalityStatus` (`mapped | not_specified | direct_amanah | unmapped_source_value | conflict`) · `municipalityNote` (`{ar,en}`; for not specified exactly «البلدية غير محددة في المصدر» / “Municipality not specified in source”) · `municipalityFlags` · `municipalitySource` = `{ value, system, field, simulated, mapping }` and the flat `municipalitySourceValue` / `municipalitySourceSystem`.
`municipalityId` is **not** the reference municipality: it stays the legacy demo component of the composite key (see Identity).
Snapshot: `byMunicipality[]` rows `{ key, amanah, amanahLabel, municipality:{ key, ar, en, refId, status }, status, count, gross, exclusions, net, collected, outstanding … }` — every invoice of an Amanah is in exactly one row (a reference municipality, `NOT_SPECIFIED`, `DIRECT`, or `UNRESOLVED` = unmapped + conflict), so the rows add up to the Amanah's total (asserted per Amanah). `snapshot.scope.muniInvalid` is true for a key that is not valid. Non-collection `byMunicipality` follows the same grouping. CSV: three columns appended at the END of `EXPORT_COLUMNS`: `municipality_ref_id`, `municipality_status`, `municipality_source_value` (`municipality_ar` is now the reference name; `municipality_id` is still the legacy composite-key component).
Helpers for other code (client + server): `src/data/municipalityModel.js` — `parseMuniKey`, `isValidMuniKey`, `amanahOfMuniKey`, `muniLabel(key, lang)` (use it, not a raw key, for any label), `municipalityFilterOptions(amanah)`, `classifySourceValues(ent, names[])`, `municipalityFields(...)`, `STATUS_LABEL`; `src/data/amanahHierarchy.js` — `municipalitiesOf(amanahKey)`, `municipalityByKey`, `amanahSelfOf`, `hierarchyIssues()`. ### Where the municipality comes from in the demo world
Real invoice-level BALADYA_KEY values are **not available**, so generated invoices get a municipality by `demoMunicipalityCode(amanah, stable invoice key, source)` — a pure function of the Amanah, the stable invoice key (a contract's invoices use the contract) and the revenue source. It is a **synthetic stand-in** and is labelled “demo stand-in” on the invoice page. Shares per Amanah (illustrative): 28 % issued directly by the Amanah, 12 % municipality not specified in source, 60 % mapped to one of the Amanah's reference municipalities (spread over all of them; never the first, never from the payer's address). White-land invoices never carry one (the source gives a city and region only) and Housing-sector invoices are issued directly. The hand-written fixtures exercise the other two statuses through the real classifier: three fixtures name a municipality that is not in the reference (`unmapped_source_value`) and one carries two disagreeing source values (`conflict`, `municipalitySourceValues` in `src/data/mock.js`). Uploaded rows have no municipality (not specified).

### Identity (composite key) — result
- **Existing keys are byte-identical**: the compact store's full key list (929 invoices) compared before / after with `cmp` (identical, md5 `9ef0cab7…`); the full world (1,718,944 records) has the same md5 before / after (`feaa3886…`); `npm run verify:identity` passes (all PASS lines).
- `ick1|inv=…|gfs=…|am=…[|mu=…]` is unchanged. The optional `mu` component still reads the **legacy** demo field (`st.muni` → `demoMunicipalityId`), which is retained only for this; the new reference municipality is a separate display / filter attribute (`st.mref`) and is never part of a key.
- **Is the municipality needed for uniqueness?** Evidence (tests + verify:identity): in the demo world number + GFS + Amanah is already unique (compact: 929 / 929 distinct without `mu`; full world: `npm run verify:identity full` → 1,718,944 distinct keys, 0 repeated, the 2 invoice numbers shared by several invoices differ by Amanah and by GFS code). So no identity change is required. Whether a real source needs it is still the open data question in `docs/invoice-composite-key.md` (BALADYA_KEY repeats across Amanahs and is only meaningful inside its Amanah). A missing municipality never merges records (every not-specified / direct row keeps its own key).

### Dependent filter — behaviour
Municipality is a **primary toolbar control right after the Amanah** on Dashboard, Collected, Uncollected, Exclusions, Decision Room and Product (mobile drawer: adjacent too). Disabled until ONE Amanah is chosen, with the placeholder «اختر أمانة أولاً» / “Select an Amanah first” inside the control (all / several → that text; the Housing Sector → «لا بلديات لهذه الجهة»). Options: «كل البلديات» first, then three explicit groups — «مباشر على الأمانة» (issued directly), «بلا بلدية (غير محددة في المصدر)» (not specified), «تحتاج مراجعة (غير مطابقة أو متعارضة)» (unmatched / conflicting source value) — then the Amanah's reference municipalities only (Jeddah: 15; the Amanah's own row is never an option). Searchable (combobox). Values are the stable keys above, never names. Changing or clearing the Amanah clears the municipality with the visible `aria-live` notice «أُزيلت البلدية لأن الأمانة تغيّرت» and removes the chip; an active chip «البلدية: …» shows otherwise. A stored municipality from the retired demo scheme («Jeddah Amanah|North»), another Amanah's municipality, or one outside the selected Amanah is reset to «all» with a visible notice (`rev.scopeNotice`) — never blank, never silently another filter. The server treats an invalid key as «selects nothing» (`snapshot.scope.muniInvalid`), never as «all». Permissions: the Amanah options are limited by `org.amanahKeys`; the server applies the same limit to every list, snapshot and CSV, and **now also to opening an invoice by id / URL** (`POST /api/invoice` returns 404 for another Amanah's invoice when the organisation is restricted).
The municipality field is 190 px wide so Period · Amanah · Municipality · fourth control fit on one row at 1360 px (checked on all six pages); Source moved to More on Exclusions and Decision Room keeps its category, Period moved to More on Uncollected (as before).

### Smart Reports: how a municipality in a request is read
Names are matched against the reference with the project's Arabic normalisation (بلدية / بلديه, ة / ه, أ / ا, tashkeel, «بلدية محافظة X» = «بلدية X»; the oddly formatted «بلدية القوز (القنفذة)» matches «القوز» and «القوز القنفذة»). The name must follow the noun «بلدية / municipality» (a bare word such as «الكامل» is never read as a municipality). English requests may use Arabic names, or the transliteration aliases defined for the Jeddah Amanah only (matching only; the UI always shows the reference name).

### Remaining
1. A bare municipality name without the noun («رابغ») is not read as a municipality (it is asked about as an unrecognised word) — deliberate: many names are ordinary words.
2. English transliterations exist only for the Jeddah Amanah; the reference has Arabic names only.
3. The municipality split is still the synthetic stand-in; no figure by municipality is real.
4. Saved Smart Reports conversations created before this change that carry an old North / Central / South key show the raw key and select nothing (they are regenerated with «تحديث التقرير» under the shared scope rules).
5. The national municipality table lists the 25 largest municipalities and one «other» row; per-Amanah detail is by selecting an Amanah.
