# Users, roles, permissions and geographic access — contract (6 Nov 2026)

Access depends on TWO things, always evaluated together and kept distinct: **(1) what the user may do** (permissions grouped by module) and **(2) which Amanahs / municipalities the user may see** (geographic scope). A role never carries a data scope; a user's **assignment** = `{ roleId, scope }` binds one role to one geographic scope, so a permission is never silently widened by another assignment's scope.

## 0. What existed before (inspected)
* Client-only login: `CREDENTIALS` in `src/data/mock.js` (`demo`, `auditor`, `admin`), session in `sessionStorage` (`ib_user`), `src/context/AuthContext.jsx`; one flag `canReview` (decisions/follow-up, exclusion upload, enforcement link actions, notes) read in `RevenueContext.jsx`; organisations (`ORGS`, `amanahKeys`) chosen at login narrow the data (Amanah level only).
* The data service (`server/api.js`) trusted whatever scope the client sent (`body.scope.org.amanahKeys`, header `x-session` = owner id of uploaded records only). No server authentication, no server-side permission check, no municipality-level restriction, no user/role administration, no audit trail.
* Settings: only «قاموس المقاييس والمصطلحات» (read-only reference). Personal preferences (language, theme) live in the header.

## 2. Geographic scope model (`src/data/geoScope.js`, pure, shared by client and server)
`GeoScope = { all: true } | { all: false, grants: Grant[], nonMunicipal: boolean }`
`Grant = { amanah: <Amanah key — the en name used everywhere (`ENTITIES[i].en`)>, municipalities: 'all' | string[] /* reference ids `MREF-…` of src/data/amanahHierarchy.js */, direct: boolean, notSpecified: boolean }`
* `municipalities:'all'` = every mapped municipality of that Amanah; an array = only those (they MUST belong to that Amanah in the verified hierarchy — validated).
* **`direct`** (records issued directly at Amanah level, municipality status `direct_amanah`) and **`notSpecified`** (the source gives the Amanah but no municipality / `not_specified`; also `unmapped_source_value` and `conflict` follow `notSpecified` so that nothing unidentified is silently granted) are explicit booleans. **Selecting a few municipalities never implies `direct` or `notSpecified`.** UI presets: «الأمانة كاملة / entire Amanah» = `municipalities:'all', direct:true, notSpecified:true`; «كل البلديات فقط / all municipalities only» = `'all'` with both false; «بلديات محددة / selected municipalities» = array with both false (the admin may tick them).
* **`nonMunicipal`**: access to records of entities that are not Amanahs / have no municipality hierarchy (central / ministry-level entities of the catalog). `{all:true}` includes everything.
* Pure helpers (names fixed): `normalizeGeoScope(x)`, `validateGeoScope(scope, hierarchy) → {ok, errors[]}`, `unionGeoScopes(a, b)`, `intersectGeoScopes(a, b)` (used to apply an organisation / filter NARROWING: result ⊆ both — never expands), `geoScopeSubset(a, b)` (a ⊆ b), `geoScopeAllowsRecord(scope, { amanah, municipalityRefId|null, municipalityStatus, nonMunicipal })`, `geoScopeAmanahKeys(scope)` (Amanah keys touched; `null` for all), `describeGeoScope(scope, lang)` → concise summary («أمانتان · 5 بلديات» / “2 Amanahs · 5 municipalities”, with «+ مباشر / + غير محددة» suffixes when granted, «كل الأمانات والبلديات» for all), `geoScopeKey(scope)` (stable string used in cache keys).
* **Per-permission effective scope**: `effectiveScopeFor(access, permissionId)` = the union of the scopes of ONLY the assignments whose role contains that permission (never the union over all assignments). Different permissions can therefore have different scopes for the same user.

## 3. Identity data model (persisted — `server/identity/`)
* `User { id, username, email?, nameAr, nameEn, avatar, status:'active'|'inactive'|'invited', assignments:[{ id, roleId, scope:GeoScope }], tokenVersion, createdAt, createdBy, updatedAt, lastLoginAt, credential:{ hash, salt, algo } | null }` — `credential` NEVER leaves the server (not in any API payload, table, log, export, audit entry or error). Password hashing = Node `crypto.scrypt`.
* `Role { id, nameAr, nameEn, descriptionAr, descriptionEn, permissions:[ids], starter:boolean, protected:boolean, createdAt, updatedAt }`.
* `AuditEntry { id, at (ISO), actorId, actorName, action, targetType:'user'|'role'|'session', targetId, summary, before?, after? }` — user create/update, status change, assignment & geographic-scope change, role create/update/delete, login failures of inactive accounts, denied privilege attempts. Never contains secrets.
* Persistence: a JSON file (`server/.data/identity.json`, git-ignored; path overridable by `IIM_IDENTITY_FILE`; written atomically; on Vercel's read-only/ephemeral filesystem it falls back to `/tmp` then to memory, and the UI states that the demo store is not durable there). Seed + **migration** (idempotent, runs on first load and on a version bump, never overwrites existing users/roles/audit): `demo` → **System Administrator**, all scope (the signed-in demo account; shown in the header as طارق) with `canReview` semantics preserved; `auditor` → **Read-only Auditor**, scope all; `admin` → **System Administrator**, scope all (title «Platform Admin»); credentials for the three seeded accounts keep their existing demo passwords (hashed server-side; the old client `CREDENTIALS` secrets are removed from the bundle). No other account is created by migration; tests create their own isolated accounts in a temp identity file.
* Guards: at least one ACTIVE user with the System Administrator role and `{all:true}` must always remain (deactivating / removing role / narrowing scope of the last one is refused); nobody can elevate their own privileges (no editing own assignments/role grants beyond what they already hold; no self-deactivation of the last admin; a non-admin with `users.manage` can only assign roles/scopes that are ⊆ their own permissions and effective scope); the System Administrator role cannot lose `users.manage`/`roles.manage`.

## 4. Authentication and sessions (the EXISTING login flow, now server-backed)
* `POST /api/auth/login {username, password, orgId?}` → `{ token, me }` | 401 `{error:'invalid_credentials'}` | 403 `{error:'account_inactive'|'account_not_activated'}`. The login page, its org selector and the `sessionStorage` session stay; the client stops holding passwords. `orgId` is a requested NARROWING, validated against the user's access.
* `POST /api/auth/activate {code, password}` — account activation / credential setup through the same login page (`/login?activate=<code>` mode): an admin creating or re-inviting a user gets a one-time activation code (shown once in the UI, stored hashed, expires, single use); no email is sent in the demo. No second authentication system.
* `GET /api/auth/me` → `me` re-evaluated live; `POST /api/auth/logout`.
* `me = { id, username, nameAr, nameEn, avatar, status, roles:[{id,nameAr,nameEn}], permissions:[ids], scopes:{ [permissionId]: GeoScope }, scopeSummary:{ar,en}, orgOptions:[{id,tier,nameAr,nameEn,amanahKeys}] /* organisations inside the user's access */, accessVersion:number }`.
* Token = signed (HMAC-SHA256, server secret from env or generated at start), carries `{uid, tokenVersion, exp}` only; every request re-reads the user: deactivation, role / scope change or password reset takes effect on the NEXT request. Every API response carries header `x-access-version`; the client refreshes `me` when it changes.
* Request header: `Authorization: Bearer <token>`. The old `x-session` (owner of uploaded records) stays but is derived from the authenticated user id server-side, never trusted from the client.

## 5. Server enforcement (every endpoint)
* `authenticate(req)` first: no/invalid token or inactive user → 401 `{error:'unauthenticated'}`; missing permission → 403 `{error:'forbidden', permission}` (no data in the body, no hint of totals).
* Endpoint → permission map (`server/endpointAccess.js`): `/snapshot,/series,/bridge` → `dashboard.view` OR any module `view` that uses the snapshot (a user who can see ANY data module may call them for their scope — documented per endpoint); `/list` → by `filters.state` / mode (`invoices.view`, `collection.view`, `exclusions.view`); `/export.csv` → the matching `*.export`; `/invoice` → `invoices.view` (+ `invoices.documents` for document payloads); `/noncollection,/worklist,/anomalies` → `collection.view`; `/distributions` → `dashboard.view|collection.view`; `/contracts,/contract` → `contracts.view`; `/enforcement-collections,/order-match,/order-debtor-invoices,/sanad-cases` → `enforcement.view` (`order-match` writes → `enforcement.review`); `/exclusion-check` → `exclusions.upload`; `/upload` & `/upload/clear` → `data.upload`; `/sources` → `sources.view`; `/quality` → `sources.view`; `/meta` → any authenticated user (labels only; no figures); `/furas/*` → `contracts.view`; `/admin/*` → `users.*` / `roles.*` / `audit.view`.
* **Scope injection**: the server computes `access = effectiveScopeFor(user, requiredPermission)` ∩ (the client's requested narrowing: organisation, filters) and puts it in the request as `body.access` (any client-supplied `access` is deleted; the old `scope.org.amanahKeys` is only a NARROWING input, intersected). All data functions (snapshot, series, bridge, list, export, noncollection, distributions, worklist, anomalies, sources, quality, contracts, contractCard, enforcement collections, order-match candidates, same-debtor invoices, detail/materialize, invoice candidates, search/autocomplete suggestions, facets, counts) apply it at the column level: an invoice is visible iff `geoScopeAllowsRecord(access, record)`. Totals, counts, facets, bridges and distributions are computed ONLY over visible records (no total, suggestion, candidate list or error message may reveal an unauthorized record: a direct id/composite key of an unauthorized invoice answers 404 exactly like a missing one; ambiguous-number candidate lists contain only visible candidates).
* **Caches**: every memo / list cache key includes `geoScopeKey(access)` + the permission; identity changes (`accessVersion`) bump the cache epoch; uploaded-record overlay keeps owner semantics.
* Admin endpoints (`server/adminApi.js`): `GET /api/admin/catalog` (permissions, starter roles, hierarchy for pickers), `GET|POST /api/admin/users`, `PATCH /api/admin/users/:id` (details, status, assignments), `POST /api/admin/users/:id/activation` (re-issue code), `GET|POST /api/admin/roles`, `PATCH|DELETE /api/admin/roles/:id`, `POST /api/admin/preview {assignments}` → effective permissions + per-permission scope summary + the figures visible under that access (count / net / collected / uncollected, labelled synthetic) so the admin sees what a user can see BEFORE saving, `GET /api/admin/audit`.

### Geographic rules (§2)
* Normal form: grants sorted and merged per Amanah, municipality refs sorted/unique, empty grants dropped, all 17 Amanahs entirely granted + `nonMunicipal` collapse to `{all:true}`; `{all:true}` has no `grants`. Unknown input normalises to the EMPTY scope (never a wider one).
* `validateGeoScope(scope, hierarchy?)` → `{ok, errors:[{code,path,ar,en,…}]}`: codes `scope_invalid`, `unknown_amanah` (the Housing Sector is NOT an Amanah; it is reached through `nonMunicipal`), `municipality_not_in_amanah`, `duplicate_amanah`, `empty_grant`, `grant_invalid`.
* Per-record rule `geoScopeAllowsRecord(scope, {amanah, municipalityStatus, municipalityRefId, nonMunicipal})`: `{all:true}` allows everything · a non-Amanah entity (flag, or an Amanah key outside the 17) → `scope.nonMunicipal` · otherwise the Amanah needs a grant, then `mapped` → municipalities `'all'` or includes the ref · `direct_amanah` → `direct` · `not_specified`, `unmapped_source_value`, `conflict` and any unknown status → `notSpecified`. A few selected municipalities therefore never imply `direct` or `notSpecified`. For hot loops `geoScopeMatcher(scope).allows(amanah, status, refId, nonMunicipal)` is the same rule precompiled.
* `intersectGeoScopes` never expands; `unionGeoScopes` is used only to merge assignments whose roles hold the SAME permission; `geoScopeSubset` is hierarchy-aware (a list naming every municipality of an Amanah is covered by «all»). `geoScopeFromAmanahKeys(keys)` converts the legacy `ORGS[i].amanahKeys` (null → all; otherwise the entire listed Amanahs, no non-municipal entities).
* A fuzz test (300 random scope pairs × every status × 4 Amanahs) checks that the set algebra agrees with the per-record rule.

### Identity store, sessions, guards (§3–§4)
* Store: one JSON document (`users`, `roles`, `audit` (cap 5000), `activations`, `schemaVersion`, `accessVersion`, `secret`), atomic writes (temp file + rename, mode 0600). Location `IIM_IDENTITY_FILE` → `server/.data/identity.json` (git-ignored) → `<os tmpdir>/iim-identity.json` → process memory. `GET /admin/catalog` and `GET /admin/users` return `storage: {mode:'file'|'tmp'|'memory', durable}` so the UI can say the demo store is not durable on Vercel. A corrupt file starts a fresh seeded store. `lastLoginAt` is kept in memory and written with the next real change (a write per login would reload the Vite dev data service, whose watcher matches `server/`).
* Signing key: `IIM_AUTH_SECRET`; else on Vercel (non-durable store) a key derived from the deployment id so all instances agree; else a random key persisted in the store. Token = `base64url({uid,tv,exp}).base64url(HMAC-SHA256)`, 12 h (`IIM_SESSION_HOURS`). Passwords: Node `scrypt` (N=16384, r=8, p=1, 16-byte random salt per password), min length 8.
* `authenticate(req)` re-reads the user and roles on every call (cached per `accessVersion`), so deactivation / role / scope changes apply on the next request; `tokenVersion` is bumped on credential change, status change and assignment change (not when a user edits only their own assignments).
* Sign-in failures: 401 `invalid_credentials` (also for unknown users, with equalised timing), 403 `account_inactive` (only after the right password; audited as `login_denied`), 403 `account_not_activated`, 403 `org_not_allowed`, 429 `too_many_attempts` (8 failures → 60 s per username). Login response: `{token, me, org}` (`org` = the validated requested narrowing, or null; the token does not carry it — the client keeps sending the narrowing per request). Activation response: same shape.
* `me.orgOptions`: ORGS whose `amanahKeys` ⊆ the Amanahs touched by the union of the user's assignment scopes (central orgs only for an all-scope user; a municipality-restricted user is offered only the organisations that add nothing beyond their access). `me.scopeSummary` = description of that union. `me` also carries `titleAr/titleEn` (the old CREDENTIALS role line) and `email`.
* Guards: last ACTIVE full administrator (System Administrator role + `{all:true}`) cannot be deactivated, downgraded or narrowed (409 `last_admin`); no self-elevation (403 `self_elevation` when a user's own new access is not ⊆ the old one, also when editing a role they hold raises their access); a non-administrator can touch only users whose current access is ⊆ their own and grant only roles/scopes ⊆ their own permissions AND effective scope (403 `forbidden` with `reason:'delegation'`; same rule for creating/editing roles with `roles.manage`); the protected role cannot be deleted/reduced (403 `forbidden`, `reason:'protected_role'`); a role in use cannot be deleted (409 `role_in_use`). Other codes: 400 `validation_error` with `fields:[{field,code,ar,en}]`, 401 `unauthenticated`, 404 `not_found`.
* Audit entries: `migration`, `user_create`, `user_update`, `user_status`, `user_assignments` (before/after scope descriptions), `activation_issued`, `user_activated`/`password_reset`, `role_create/update/delete`, `login_denied` (inactive account), `access_denied` (missing permission or guard refusal; the same attempt is recorded once per minute). Each entry has Arabic `summary` and English `summaryEn`, `actorName` (Arabic) and `actorNameEn`. No secret is ever written; activation codes exist in plain text only in the single response that hands them to the administrator.
* Routes (all JSON, `Authorization: Bearer`): `POST /auth/login|activate|logout`, `GET /auth/me`; `GET /admin/catalog`; `GET|POST /admin/users`, `GET|PATCH /admin/users/:id`, `POST /admin/users/:id/activation`; `GET|POST /admin/roles`, `PATCH|DELETE /admin/roles/:id`; `GET /admin/audit?limit&offset&action&targetType&targetId&actorId`. `/admin/preview` is answered by `server/api.js` (uses `resolveAccessFromAssignments` + `describeAccess` from `server/adminApi.js`). Every identity response carries `x-access-version`.

## Implementation notes — server enforcement (agent E1, 6 Nov 2026)

### Files

### Request flow (`handleApi`)
1. `/auth/*` and `/admin/*` (except `/admin/preview`) go straight to `handleIdentityRoute` (login / activation are the only unauthenticated routes). Every response carries `x-access-version`.
2. Everything else: `authenticate(req)` → **401** `{error:'unauthenticated'}` (no token, bad signature, expired, inactive user, stale `tokenVersion`) — an unknown path is also 401 for an anonymous caller. The client-supplied `x-session` / `session` / `body.owner` are ignored; the **owner of uploaded records is the authenticated user** (a per-process registry user id → 1…60000, no hash collisions).
3. `requiredPermissionFor(method, path, body)` → **403** `{error:'forbidden', permission, anyOf?}` (a denied attempt is written to the audit trail by the identity module; nothing else is in the body). Unknown endpoint → 404.
4. **Scope injection**: `granted` = the permissions of `anyOf` the user holds; `access = ( ∪ effectiveScopeFor(user, p) for p in granted ) ∩ narrowing(body.scope)` where the narrowing is built from `scope.org.amanahKeys` / `scope.orgKeys`, `scope.amanah` and `scope.muni` — it can only shrink. `body.access` is **deleted then set**; `body.owner` is overwritten. The engine additionally ANDs the same org / Amanah / muni filters, so a narrowing is applied twice, never widened.
5. Identity change (`accessVersion` differs from the last one seen) → the access tables, the list cache and the memo are dropped; caches are in any case keyed by `geoScopeKey(access)` + the granted permissions.

### Visibility (`server/accessMask.js`)
An invoice row is visible iff `geoScopeAllowsRecord(access, { amanah: ENTITIES[st.ent[i]].en, municipalityRefId, municipalityStatus, nonMunicipal: st.ent[i] ≥ N_AMANAH })`. Both inputs are small integer columns (`st.ent`, `st.mref`), so the decision is taken once per (entity, municipality code) pair into a `NE × MUNI_SLOTS` byte table cached per `geoScopeKey` (64 entries, LRU) and read per row in O(1): `accessTable(access)`, `isVisible(st, i, tab)`, `visibleMask(st, access)` (a byte mask over the rows, cached per scope key + store + row count), `accessKeyOf(access)`. `access` absent / `{all:true}` = unrestricted (direct callers in tests and scripts); an object that is not a GeoScope denies everything. Uploaded and hand-anchored rows carry the same two columns, so they are covered automatically (an upload has no municipality = «not specified»).

`makeCtx` reads `req.access`; `resolveScope` folds it into `entOk` (entity reachable at all) and `inScope` tests the table — so **every function that already scopes through `resolveScope` / `inScope` is covered**: snapshot (totals, byAmanah / bySource / byMonth / byMunicipality / matrix / quality ids / top-K ids), series (including the large-payment list), bridge, `candidates` → `list` / facets / `exportChunks`, `worklist`, `anomalies`, `noncollection` (all populations, byAmanah / byMunicipality / bySource, heat, groups, standing balance, bridge, the `invoices` appendix through `list`), `distributions` (including the Amanah → municipality → source tree), `quality`, `enforcementCollections`. The new `resolveScope().key` starts with the access key.

Functions that do not go through `inScope` apply the same table explicitly: `invoiceCandidates` and `/invoice` (lookup by legacy id, composite key or bare number — only visible rows take part, so an unauthorized invoice answers 404 `{error:'invoice_not_found'}` byte-identical to a missing one, an ambiguous number lists only the visible candidates, and ONE visible match opens without hinting at the others), `resolveSearch` (contract number, CR number, enforcement number, ids — only visible contracts / requests resolve), `resolveReferences` and `sameDebtorInvoices` (orderMatch), `checkExclusionRows` (an unauthorized invoice → `invoice_not_found`, never `other_amanah`), `sourcesReport` (loop, fixtures, request counts; its integrity checks still read neighbours structurally but count only visible records), `meta` (invoice / payment / contract / request counts), `/upload` (a record outside the uploader's `data.upload` access is returned in `outOfScope` and not stored).

### Contracts, requests, Furas
* A generated contract is visible iff the user may see its Amanah + its municipality (the same `demoMunicipalityCode` seed as its invoices) **and every invoice linked to it** (fail closed). The compact world has one contract of the Eastern Province whose invoices partly sit in the Jeddah Amanah (generator artefact): it is visible only to an access that covers both. `contractCard` counts only visible records for the ambiguous-number answer.
* A Sanad / white-lands request is visible iff its contract (if any) and every invoice it identifies or covers are visible; one that names neither is read as «Amanah known, municipality not specified». `sanadCases`, the contract card's request list, `meta`, `quality`, `sourcesReport` use this.
* **Furas dataset mode**: its records carry only the source `MUNICIPALITYID` / `MUNICIPALITY` whose mapping to the verified Amanahs / municipalities is **not confirmed** (`confirm_entity_scope`). They cannot be attributed to a geographic scope with certainty, so the dataset is served only to a user whose `contracts.view` access is «all»; any narrower access gets `/furas/status → {available:false, reason:'geo_scope_unmapped'}` and 404 `furas_unavailable` elsewhere. When the Furas ↔ Amanah mapping is confirmed, apply the table to its rows and drop this rule.

### Deliberate decisions (and what is not scoped)
* **Priority thresholds** (`amountThresholds` in `lists.js`): the 75th / 90th percentile amounts that classify an invoice's priority stay store-wide (so one invoice keeps one priority whatever the viewer's scope). They are two aggregate numbers, not a record or a count, and are never returned.
* **Report-only («unmatched») rows** of the bridge are national: a user whose access is narrower than «all» gets none, and `nationalCount` / `nationalAmount` read 0 (`scopedOut:true`).
* `quality` request / chain / CR counts and `meta.generation.contracts|requests` follow the visible contracts and requests; `crViewKnown` counts the CR numbers of the visible contracts and requests.
* The invoice's own attributes (`contractNo`, enforcement order number, `duplicateOf`) are shown with the invoice; opening the contract or the order is still refused when it is outside the access.
* `/admin/preview`: the previewed permissions and per-permission scopes come from `resolveAccessFromAssignments`; the figures (count, gross, exclusions, net, collected, uncollected — synthetic, labelled) are computed under `preview scope ∩ the administrator's own data-view scope`; `clamped:true` says when the two differ, `figures:null, figuresWithheld:true` when the administrator holds no data-module view. `modules.<module>.records|contracts|requests` give cheap per-module visible counts.
* The Vite dev watcher reloads the data service when any file under `server/` changes, **including `server/.data/identity.json`** (audit entries of denied attempts are written there): ignore `server/.data/**` in `vite.config.js` if that becomes disruptive.

### Session and sign-in
Password → `POST /api/auth/login {username, password, orgId?}` once; only `{token, me, orgId, orgScoped}` is stored (tab-only `sessionStorage`); the password field is cleared after the call and never logged. On start a stored session is re-validated with `GET /api/auth/me` (401 → signed out, with a notice on the login page: «انتهت الجلسة…»); the older `ib_user` key is discarded. Server errors are shown in AR/EN (`authErrorText`): invalid credentials, deactivated, not activated, too many attempts, organisation not allowed, invalid/expired activation code, weak password. The login page offers every organisation as a REQUESTED narrowing (the list is public labels only); if the service answers `org_not_allowed` the page signs the person in with their own full access instead (never wider). After sign-in the header selector lists only `me.orgOptions`; a person who holds no data module gets no organisation control. `src/data/mock.js`: `CREDENTIALS` removed (no password in the bundle); `DEMO_ACCOUNT_HINTS` keeps the three demo display names only; `ORGS` unchanged.

### API client
`Authorization: Bearer <token>` on every call; no client-chosen identity (`x-session` removed — the owner of uploaded records is the authenticated user, decided by the service). Cached answers are keyed by `epoch | token | path | body` (another person never sees a cached answer; the epoch is bumped on sign-in/out and whenever the person's access fingerprint changes). 401 → `session.noteUnauthenticated(token)` signs out only if that token is still the current one; 403 → `ForbiddenError` (`isForbidden(e)`, `.permission`, no data); `x-access-version` changes → `refreshMe()`, so permission / scope changes of a role apply to the open tab without signing in again (an assignment or status change bumps `tokenVersion` on the server, so that person is signed out on the next request with the message). The CSV link sends the signed expiring token as `access_token` (the one parameter `/api/export.csv` accepts).

### `useAccess()` (exact shape)
`{ me, ready, can(id), canAny(ids), scopeFor(id) → GeoScope, geoScope /* union of the scopes of the data-module permissions (the nine DATA_VIEWS + sources.view) */, scopeSummary(lang) → string, accessVersion, orgNarrowing /* GeoScope | null */, effectiveScope(id) /* = scopeFor ∩ orgNarrowing */, refresh() → Promise<me|null>, permissions: Set, canReview, gates, gate(actionKey), accessKey, allScope }`. A held permission with no entry in `me.scopes` is treated as EMPTY (never wider than the service stated). Outside the provider / signed out nothing is allowed.

### S3. Geographic access — three options only (UI), same `GeoScope` underneath
1. **All entities and municipalities** → `{all:true}`.
2. **Selected Amanahs — all their municipalities** → one grant per Amanah `{municipalities:'all', direct:true, notSpecified:true}` (the whole Amanah).
3. **Selected municipalities under selected Amanahs** → per Amanah `{municipalities:[…], direct:false, notSpecified:false}`; municipality choices depend on the selected Amanah.
A municipality-restricted user (option 3) gets NO direct-Amanah or unspecified-municipality records unless the administrator ticks ONE explicit checkbox, «تضمين سجلات الأمانة المباشرة والبلدية غير المحددة / Include Amanah-level and unspecified-municipality records», which sets both flags for the selected Amanahs. ### S4. Enforcement (same server mechanism)
`endpointAccess.js` maps endpoints to MODULES (any-of): `/snapshot,/series,/bridge,/meta` → any data module; `/list` + `/export.csv` → by mode: collected register → `invoices_collected`, uncollected/open/noncollected/worklist modes → `invoices_uncollected`, exclusions register → `exclusions`; `/invoice` → `invoices_collected|invoices_uncollected|exclusions|enforcement`; `/noncollection,/worklist,/anomalies` → `invoices_uncollected` (anomalies also `exclusions`); `/distributions` → `dashboard|invoices_uncollected`; `/contracts,/contract,/furas/*` → `contracts`; `/sanad-cases,/order-match,/order-debtor-invoices,/enforcement-collections` → `enforcement`; `/exclusion-check` → `exclusions`; `/upload,/upload/clear,/sources,/quality` → `data_sources`; `/admin/users*` → `users`; `/admin/roles*` and `/admin/catalog` → `roles` or `users`; `/admin/audit` → `users` or `roles`; `/admin/preview` → `users` or `roles`. Module off ⇒ 403 for the request AND its exports; module on ⇒ data masked by the user's scope. Permission/role/scope/status changes apply on the next request (`accessVersion`, `tokenVersion`); at least one ACTIVE Administrator with scope `{all:true}` always remains; no self-elevation (a user cannot edit their own role or scope).
### S5. Migration (idempotent, schema version bump; audit history preserved)
Old roles → new role records: each old role's permission ids are mapped to modules (a module is ON if the old role held any permission of that module; `invoices.*` → `invoices_collected`+`invoices_uncollected`; `collection.*` → `invoices_uncollected`; `reports.*` → `smart_reports`; `sources.view`/`data.upload` → `data_sources`; `users.*` → `users`; `roles.*`/`audit.view` → `roles`; `metrics.view` → `metrics`; and so on); `readOnly` = true when the old role held no upload/manage/review/followup/update permission (e.g. the old Read-only Auditor). Old users with several assignments → ONE role + ONE scope: the first assignment is kept (documented in the audit entry with the dropped assignments listed); `demo` and `admin` stay Administrator with `{all:true}`; `auditor` → Auditor role (read-only) with `{all:true}`. Existing audit entries, notes and accounts are preserved.
